## 一、为什么改口径

### 1. `phases`：量到了渐变中间帧

`FADE_MS = 900`，按累计 delta 推进；`?time=noon` 只是把目标定在 noon，页面加载后仍要
走完 900ms 渐变。冷启动时墙钟 2200ms 里游戏时间推进不足 900ms，截图拍在过渡中：
noon 被拍成比 dawn 还亮的 66.10（正常稳态是 58.9），差 -0.68 被判红。
这不是渲染坏了，是**采样点没落在稳态**。

改法：每个刻度的页面等 `window.Oracle.ecoState().advanceCount` 再推进 60 帧（≈1s）才截图；
外加一整轮不计分的预热跑（四刻页 + 夜雨页，读数丢弃）。

### 2. `render-budget`：量的是「逻辑步进节奏」，不是「上屏帧」

旧判据比的是 `advanceCount`（世界步进次数）中位：恢复 41 vs 前台 57 就是 0.72，
判红。但同一段里 rAF 稳定在 59.9——**上屏一点没掉，掉的是场景自己跳帧的节奏**。
隐藏期间 rAF 被掐掉，回前台后合成器、Phaser 步进都要重新起转，整段中位天然带爬升尾巴。

改法：

- 末秒判据：恢复段**最后 1 秒**的 rAF 间隔中位 ≤ 前台间隔中位 ÷ 0.9
  （等效「末秒帧率 ≥ 前台 × 0.9」，阈值 0.9 不变）。
  注意方向：间隔越小越快，写成 `间隔 ≥ 前台 × 0.9` 会变成「恢复不许比前台快」，与原意相反。
- 逐秒硬底线：恢复段**任何一个 1 秒窗口**的帧率 ≥ 前台 × 0.5（新增，只更严）。
  专防「先崩到 15 帧、末秒爬回 59.9」被尾巴判过。
- 读数全打出来：恢复整段中位、末秒中位、4 个逐秒窗口帧率、前台帧率、推进口径。

### 3. `daily-prop-cost`：墙钟量的是「机器有多忙」

单次墙钟在 `node --test` 并行跑时夹着排队时间：同文件相邻用例全过，只有这条红，
实测 54.62ms / 100.28ms，而文件头常态 0.3–5ms。主指标改为 `process.cpuUsage()`
前后差（user + system），预算仍 50ms；墙钟降为 diagnostic 附注。

Windows 上进程 CPU 记账跟调度时钟走（约 15.6ms 一格），一天传播不到一格时会读成
`0.00`。历史口径是「读成 `0.00` 就重采、最多三次、**取最大值**」（理由：真退化成
60ms 的那次若和两个 0 平均成 20ms，回归就被糊掉了）。

**2026-11-04 改为「固定采三次、取最小值」**：`取最大` 在 CPU 口径上是错的方向——
并发 GC/编译线程的 CPU 也算进本进程，8 路并行 64 次抓到一次 `CPU 62.00ms /
墙钟 16.64ms`（CPU 比墙钟大 3.7 倍），取最大把一次 GC 停顿直接放大成红。
噪声只往上加，真退化是确定性的。对照读数与并存性分析见本文第七节。

## 三、预热做了什么（为什么这不等于放宽）

- `phases`：正式轮之前，把四刻页 + 夜雨页按同一路径完整跑一遍，均值只打日志
  「`[预热轮] 不计分`」，不写截图、不判定；正式轮另开页面，自己必须过全部 17 项。
- `render-budget`：正式轮之前，另开一个页面跑完整测量（静止 4×1s、拖动、前台 4×1s、
  后台 4s、恢复 4s，约 20–25s），读数丢弃后关页；正式轮另开新页并清 `localStorage`，6 项自己过。
- 覆盖的是**进程级一次性成本**：bundle 解码、脚本 JIT、GPU 频率爬升、GPU 进程内
  ANGLE 程序缓存。诚实地说：正式页仍要为自己的 WebGL 上下文编译着色器/上传纹理，
  所以预热吃不掉全部冷启动——`render-budget` 仍有余量在 CI 上偶发红。

## 五、残余风险

1. **CI runner 的软件渲染冷启动本机复现不了**（CI 恢复 26–31 vs 前台 32–38）。本机能复现
   红，但严重程度不同；新判据在 16 核 Windows 上 10 次只红 1 次，CI 上仍需实跑确认。
2. **rAF 判据的分辨力来自相对值**：headless 被 vsync 钉在 59.9，所以真正有信息的是
   「逐秒是否掉下去」。若 CI runner 的 rAF 上限本身是 30，「末秒 ≥ 前台 × 0.9」仍成立，
   但读数会整体变小。
3. **`0.00` 的残留是分辨率边界**：3/20 是三次重采全 0（真低于一格），重采解决不了；
   闸只能抓 ≥50ms 的量级退化（真退回全库扫描是几十毫秒，跨得过刻度）。
4. **预热让闸门变慢**：phases 37–49s → 87–182s；render-budget 45–56s → 63–92s（预热）
   → 84–109s（预热 + rAF 采样）。
5. **`传播的代价随规模走` 偶发红**（half 10.57ms vs all 1.38ms）：已由 `fix/flaky-gates`
   修掉——一天的真实计算量只有 0.3~1.0ms，单次墙钟采样采到的是调度停顿；改成预热 +
   5 轮交错取最小，判据 `half < all * 2` 未动。取证见 `BUGS_FOUND.md` 附。
6. 三道闸共用同一台机器时互相干扰；正式读数请单跑，别和 busy loop 抢核。

## 七、2026-11-04 追加：规模对照与方向闸的采样口径（`fix/flaky-gates`）

绝对预算闸仍走本文档第二节的 CPU 时间口径（`feat/gate-warmup`，50ms 不变）；
本节只改**对照/方向**两处的采样口径，阈值一个没动。

**为什么要改**：空载实测一天的 tick 只有 0.3~1.0ms，而并行时一次调度停顿就是
5~100ms。探针把每次采样打出来后，顺序一反转就换哪组「变贵」：

| 采样顺序 | 第 1 个样本 | 第 2 个样本 | 第 3 个样本 |
| --- | --- | --- | --- |
| half → all | half 29.56ms | half 9.95ms | half 0.81ms / all 0.90ms |
| all → half | all 18.62ms | half 1.98ms | all 1.18ms |

即「哪组先采样哪组贵一个量级」——首次 `dayClosed` 的 JIT/首次分配，与规模无关；
`min-of-3` 只在「至少一个样本没撞上停顿」时救得回来。

**改法**：

| 位置 | 改前 | 改后 | 判据 |
| --- | --- | --- | --- |
| 规模对照 | 3 轮交错，无预热 | 1 轮不计时预热 + 5 轮交错，取最小 | `half < all * 2`（未动） |
| 第 6 天方向 | 两边各单次采样 | 两边各 3 次取最小 | `steady < day1 * 2`（未动） |
| 第 1 天绝对闸 | CPU 时间，`0.00` 时重采、取最大（main 口径） | CPU 时间，固定 3 次取最小 | `< CEILING_MS 50`（未动） |

**读数**：预热 + 5 轮后 `half/all` 稳定在 0.53~0.61（3 轮时偶见 0.89~1.02，正是
「三轮不够」的现场）；反向验证（把 `half` 换成 400 个 holder，真的让小的更大）
立刻红：`N=5 FAIL(2.29/0.71=3.24)`、`N=7 FAIL(2.15/0.54=4.01)`。
8 路并行 64 次、16 路并行 64 次：0 红（改前 8 路 64 次红 3 次全部是绝对闸，
规模断言另有 1/32 红、读数 10.63ms / 4.09ms）。

**这不是放宽**：噪声只会把读数往上加，最小值是「没有噪声时该花多少」的估计；
两边用同一个估计量、只增加采样轮数，阈值与用例数都没动。

### 七.1 「CPU 口径」与「取最小」能不能并存

结论：**能**，但有一个已知的灵敏度代价。两条主张的适用范围不重叠：

- CPU 口径解决的是**计量单位**：把「被换出去的墙钟」从读数里去掉。它抓的是
  「这一天的确定性开销有多大」。
- 取最小解决的是**估计量选择**：单次样本会被一次性噪声（JIT、首次分配、GC、
  调度停顿）单向上加，min-of-N 是「没有噪声时的开销」的下界稳健估计。
- 二者不冲突，因为闸要抓的退化是**确定性**的：传播改成每步全库扫描，是每一拍都贵，
  不是偶尔贵。对确定性开销，每个样本都 ≥ 真值，min 仍是真值的上界且量级不丢。

对照读数（同一台机器，`fix/flaky-gates` 合并后）：

| 口径 | 场景 | 次数 | 红 | 读数 |
| --- | --- | --- | --- | --- |
| CPU，`0.00` 重采、取最大（main） | 8 路并行 | 64 | **1** | CPU 62.00ms / 墙钟 16.64ms |
| CPU，固定 3 次取最小（本节） | 8 路并行 | 64 | 0 | 三次 0.00 / 0.00 / 0.00，墙钟 0.46ms |
| 同上 | 16 路并行 | 64 | 0 | — |
| 同上 | 16 个忙等进程压满 CPU | 1 | 0 | 三次 16.00 / 0.00 / 0.00 → **取最小 0.00**，墙钟 0.53ms |
| 同上 + 注入 400ms 忙等 | — | 1 | **1** | 三次 422.00 / 390.00 / 407.00 → 取最小 **390.00ms > 50** |

第三、四行是这套口径的代价，要写清楚：**取最小会把「偶发的慢路径」也一起剔掉**。
如果哪天退化只发生在三次里的一次（比如每三拍才命中一次慢分支），这道闸读不出来——
抓那种退化的应该是单次回归基准（固定机器 + 单独 benchmark），不是这条 50ms 的噪声闸。
反向验证（第五行）证明「确定性退化」不漏：400ms 忙等三次全部跨过记账刻度，
最小值仍是 390ms，立刻红。

方向闸（第 6 天）同理，只换成墙钟：第 6 天的 CPU 差值在 Windows 上会读成 0.00，
`0 < 0 * 2` 恒假，所以两边都用同一套 min-of-3 墙钟（读数 0.16ms vs 0.46ms）。

## 八、2026-11-06：压暗探针上限 6 s → 8 s（CI 抖动，不是放宽）

| 本地（Windows，16 逻辑核） | 319 / 496 / 571 / 578 / 840 ms | 3–14 | 远低于 6 s |
| 共享 CI runner（GitHub Actions） | **6217 ms** | **25** | 卡在 6 s 门槛上 |

8 秒相对最差观测值（6217ms）留了约 1.8 s 余量（约 29%），只覆盖机器速度差。

**这不是放宽——反向用例实测**：新增 [check-phases-negative.mjs](file:///D:/project/pwe-material/world-client/scripts/check-phases-negative.mjs)，
夜里先下雨（雨幕逐帧都在动），再对**整块画布**跑同一个 `waitFadeSettled`
（默认 8 s 上限）与同款 `check(...)` 断言。2026-11-06 实跑：

```
[反例] weather=rain say=ok
[反例] probe waitedMs=8139 frames=56 capMs=8000 settled=false
FAIL night（雨幕）压暗层 8 秒内收敛  等待 8139ms / 56 帧
[反例] 反例成立：雨幕逐帧在动，8 秒后仍未收敛 → 闸门判红。
exit=1
```

即：真的不收敛，8 秒后照样 `settled:false`、照样 FAIL。该脚本**期望红**，不进 CI 绿闸。

**这条反例也暴露了两个口径问题**（已记 [OPEN_ISSUES.md](file:///D:/project/pwe-material/docs/OPEN_ISSUES.md) E3）：

1. **墙钟判收敛本身脆**：阈值只能覆盖已知机器；换更慢的 runner，8 s 也未必够。
2. **小样区会假收敛**：26×26 的草地样区在雨里经常连续三帧没有一颗雨滴穿过，
   探针会误报 `settled:true`（同场景实测 2146ms / 15 帧就「收敛」了）。反例因此改用整块画布；
   晴天的压暗层仍用原小样区（那里只该有静态地面）。
