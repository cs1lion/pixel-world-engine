# 这套环境能不能在本仓建起来：逐阶段评估

> 口径说明：本文中的测量值若非判据，一律标注日期或改为取当前值的命令；判据（阈值、面积上限、块数上限、预算、路径清单）保持写死。
>
> 评估日期：2026-11-06。评估对象：`D:\project\pixel-world-engine` 的 `main`（`0f71d9c`）。
> 标注：`[实测]` 本轮实际运行；`[证据]` 读自已归档的证据文件；`[文档]` 只有书面记录、没有执行判据。

## 总判断

**这套方法论在本仓能由闸门强制的那一半，是「结果形态可复算」——引用存在、色板预算、测试通过、截图逐像素差、账本字段；另一半「过程顺序与第二方判断」——先读透再规划、先红后绿、多模型竞技、作者不自批、swarm、跨家族互审——在本仓没有机关，只能靠流程纪律；而且当前的实际交付路径是本地 `--no-ff` 合 main 加 `PWE_ALLOW_PUSH_MAIN=1` push，连已经写好的 `CODEOWNERS` 与 PR 模板都没有进入执行。**

换句话说：**闸门管「做出来的东西长什么样」，流程管「东西是怎么做出来的」。** 前者本仓已有相当厚的一层，后者只有零散留痕，没有一条能在 AI 不照做时自动发现。

## 1. 规划

### 1.1 `how`：动工前读透相关模组、建立全局观

#### 本仓现状

**已存在（有文件，部分有闸）**

- `CLAUDE.md` 给出仓库结构与权威边界：`docs/SPEC.md` 是唯一权威，禁止新增 `SPEC_*` 文件；迭代资料在 `docs/iterations/`；美术设定在 `docs/art/`。这不是口号——`audit-claims` 的 `spec-authority` 探针会数 `SPEC` 文件数、检查唯一权威标记和 `SPEC_V2.md` 的历史归档标记，对不上就红（`world-client/scripts/audit-claims.ts`）。
- `docs/agents/domain.md` 明确要求「探索代码库之前先读 `GLOSSARY.md` 与 `docs/adr/`」，并规定输出要使用 `GLOSSARY.md` 的词。这是本仓对「先建立全局观」的书面约定。
- `docs/adr/` 当前有 10 份 ADR（2026-11-06 本地读数：`adr-schema` files=10 valid=10；跑 `node world-client/scripts/audit-claims.ts --strict` 取当前值）；`audit-claims` 同时校验 ADR 的 `status / verified_at / evidence` 字段与证据路径。
- `docs/iterations/README.md` 把外部设计资料按迭代任务分组，并写明「原样收存，附索引；不代表已排期」，还用 `<!-- claim: iterations-tracked-count=12 -->` 钉住入库文件数。

**部分存在**

- 上述都是「读什么」的指引，不是「必须交一份读过的证据」。`audit-references.ts` / `audit-citations.ts` 能查文档里的引用是否指向真实文件，但**一份计划可以完全不引用任何模组就通过所有闸门**。
- 没有「本次改动会影响哪些模块」的清单，也没有依赖图或调用面工具。`OPEN_ISSUES` B4 曾指出世界变大后的三处隐患，说明这类全局影响目前靠人读代码发现。

**完全没有**

- 没有规划产物闸：没有 `Plan-Doc:` 之类的提交 trailer，没有「动到核心路径必须先提交计划」的检查。
- 没有「读过的文件清单」或「被否掉的候选架构」的必填字段。

#### 能否构建

**有条件能。** 条件：

1. 先写一份计划模板，要求列出「要动的模块（带文件链接）」「现有可复用的抽象」「至少一个被否掉的方案」「验收命令与判据」。
2. 在本地合并前或 pre-push 里检查：动到核心路径（`world-client/src/world/`、`world-client/src/render/`、`server/`、存档契约）时，提交必须带 `Plan-Doc:` 指向一份仓内文档；该文档里的文件引用必须能被 `audit-references` / `audit-citations` 解析。
3. 条件不满足时拒绝合并/推送。

**做不到的部分**：工具无法证明作者真的「读透」。计划可以只列三个文件名，照样解析通过。**「读透」只能靠抽样或外部核对。**

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 计划文档存在；计划里的文件引用存在；核心路径改动带 `Plan-Doc:` | 计划是否真的覆盖了相关模组；是否读过被引用文件的内容；是否建立了全局观 |

**AI 不照做时能不能发现？**

- 「完全没写计划」：能发现，前提是闸门覆盖了该路径且没有被 `--no-verify` / 豁免 push 绕过。
- 「写了计划但没读」：**不能自动发现**。可发现的方式只有三种：① 计划评审时由另一个模型/人核对「它列的模块是否漏了明显相关项」；② 抽查计划里的引用是否只是文件名堆砌；③ 事后用 bug 归因反查「这次冲突是不是因为漏读某个模块」。
- 当前实际：以上三种都没有制度化。

#### 构建代价与判据

- **新增**：一份计划模板 + 一个路径清单 + pre-push 或合并脚本里的 trailer 检查。`audit-references` / `audit-citations` 可直接复用，不需要新解析器。
- **代价**：小到中。主要成本不在脚本，在「核心路径清单」会漂——`OPEN_ISSUES` E1 已经说明 `SandboxScene.ts` 这类文件同时承担渲染、调试、状态写入，边界本来就模糊。
- **建成后怎么证明真起作用（反向样本）**：
  1. 故意在 `world-client/src/world/simulation.ts` 做一处改动，不带 `Plan-Doc:` → 推送/合并必须被拒。
  2. 故意让计划引用一份不存在的计划文档（例如 docs/FAKE_PLAN.md）→ `audit-citations --strict` 必须红（这一类本仓已经吃过：`docs/evidence/INDEX.md` 记录 2026-11-06 有 22 处未解析引用 + 5 处行号存疑导致 main CI 红）。
  3. 反向样本 2 是**现成可用的**，不需要新建；反向样本 1 需要新建。

#### 风险：最可能在哪一步半途而废

**计划写成「事后补的文档」。** 原因很具体：本仓现在没有 PR 流程，合并是本地 `--no-ff`，计划文档可以在代码写完后再补；而 `audit-references` 只查引用存在，不查写作顺序。一旦补文档能过闸，闸门就退化成「多写一个 md」。第二个风险是核心路径清单漏项——`OPEN_ISSUES` 里 A/B/E 三条已经显示存档、渲染、调试面互相咬合，清单很难一次列全。

### 1.2 `why`：去翻 git 记录、工单、文档，挖出「前人踩过什么坑」

#### 本仓现状

**已存在（有文件，部分有读数）**

- `docs/adr/` 有 10 份 ADR（2026-11-06 读数，份数以命令为准），写的是「为什么不是另一种做法，以及另一种会坏在哪里」；`audit-claims` 校验字段与证据路径。
- `docs/DECISIONS_20261102.md` 是一份真实的「岔路记录」：D11 把真实时钟设为默认，D13 又改回游玩时间驱动，并写明理由「页面没运行时世界不能积累信息……按墙钟补算等于伪造」，还写了回退方式。**这正是 `why` 想要的形状**：不是只写结果，而是写下「上一版为什么被推翻」。
- `docs/evidence/PROGRESS.md` 每个块都有「被否掉的写法及原因」栏（例如块 2 记录了把「避让」硬塞成 `Goal | null` 为什么不行）。
- `docs/BUGS_FOUND.md` 对每个 bug 写「修复前读数 / 修复后读数 / 影响范围」，而不是只写「已修」。
- `docs/OPEN_ISSUES.md` 用 `[事实]` / `[推断]` 分栏，每条带证据链接与「是否需要用户决策」。

**部分存在**

- 这些是**部分改动的留痕**，不是每次改动都必须留下的字段。没有规则要求「动到防御性代码时必须链接一段历史」。
- `git log` 本身可查，但没有脚本把「这次改动动的这行代码是哪个提交加的、为什么加」拉出来。`git blame` 靠人手动。
- `OPEN_ISSUES` 里已有「前人踩坑」的直接证据：D5 记录「回家后还问不问规则表」的截断问题、D6 记录冻结轨迹不覆盖 homecoming 的判据盲区、E3 记录压暗收敛用墙钟判本身脆。这些是「写了」，但没有变成「改回家线前必须查 D6」的机关。

**完全没有**

- 没有 `Why-History:` 之类的 trailer。
- 没有「防御性代码清单」：哪些写法看起来绕、但其实是防呆，目前只散落在 ADR 与 issue 里。

#### 能否构建

**有条件能。** 条件：

1. 维护一份「防御性代码/历史坑」清单，或者复用 `docs/adr/` 与 `docs/OPEN_ISSUES.md` 的编号。
2. 动到清单里的路径时，提交必须带 `Why-History:`，指向一个存在的 ADR、issue 编号、或 commit sha；脚本用 `git cat-file -e` / `gh issue view` / 文件存在性校验。
3. 合并前由另一个人或另一个模型核对「这条历史链接是否真的解释了这段代码」。

**做不到的部分**：链接存在不等于读过；作者可以链一个无关的 commit。**只能靠外部核对。**

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 历史链接存在、指向对象存在 | 链接是否相关；是否真的从历史里挖出了「为什么这么绕」；是否因此保留了该保留的防呆 |

**AI 不照做时能不能发现？**

- 「没链历史」：能发现（如果路径清单覆盖）。
- 「链了但不相关」：**不能自动发现**。可发现方式：① 另一个模型审 `Why-History` 链接与 diff 的相关性；② 事后 bug 归因——如果一次「优化掉防呆」导致旧 bug 复活，回查提交里有没有历史链接；③ 抽样人工读。
- 当前实际：没有一条在执行。

#### 构建代价与判据

- **新增**：路径清单 + trailer 校验；复用 ADR/issue 编号，不需要新数据库。
- **代价**：小到中。难点是「防御性代码清单」本身会漂；`OPEN_ISSUES` E2 已经暴露「登记表会退化成摆设」的风险——如果清单只增不减，人会开始链无关条目。
- **反向样本**：
  1. 动 `world-client/src/world/save.ts` 时不带 `Why-History:` → 拒绝。
  2. 带一个不存在的 commit sha → 拒绝。
  3. 带一个存在但无关的 ADR → 工具会放行；这一条**必须由外部核对兜底**，不能假装闸门能判。

#### 风险

**最容易半途而废的是「历史清单变成 ADR 坟场」**：每条新坑都加一条，没人回收，最后作者为了过闸随便链一条。`OPEN_ISSUES` E2 已经用工作树登记表演示过这个失败模式：strict 红失去可读性后，人会「补账转绿」，登记表退化成摆设。

### 1.3 `sharpen`：交任务前先升级 prompt，三视角 + 验收条件

#### 本仓现状

**已存在**

- `.github/pull_request_template.md` 有「改了什么 / 为什么 / 验证命令与读数」三栏，验证栏逐条列出九道闸门与 `check:hooks` / `worktrees:audit`，并写明「至少贴一条真的跑过的命令和它的输出首行；没跑的写『未跑』」。
- `docs/RESUME.md` 要求中断记录写「下一步命令」而不是「下一步目标」，并规定读数贴输出首行。这是「验收条件可执行」的局部实践。
- `docs/evidence/VERIFIABLE_FLOWS.md` 把自己的流程写成「触发命令 + 判据 + 反向用例 + 产物落点」，已经是 prompt 里「怎么证明真做对了」的形状。

**部分存在**

- PR 模板是**变更后**的读数栏，不是**动工前**的 prompt。它回答「跑过什么」，不回答「这件事怎样才算对」。
- 模板没有「顶尖老手会做而容易漏的步骤」「第一性原理/一手资料」「用什么客观方式证明」这三栏。
- 模板没有被执行：本仓合并走本地 `--no-ff`，没有 PR；`git log --merges` 里没有 PR 号。

**完全没有**

- 没有 prompt 升级产物，没有「验收条件先于实现写定」的检查。
- 没有「任务开始前先写判据」的模板或脚本。

#### 能否构建

**有条件能（仅限模板与留痕）。** 条件：

1. 每个非平凡任务先落一份 `docs/prompts/<topic>.md`，至少写：领域老手会漏的步骤、一手资料/源码位置、验收命令与判据、反向样本。
2. 合并前检查该文件存在且四个字段非空；验收命令里的脚本/文件必须存在（可复用 `audit-citations`）。

**做不到的部分**：无法证明 prompt 是在动工前写的，也无法证明它真的影响了实现。**质量只能靠外部核对。**

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| prompt 文件存在；字段非空；命令/路径存在 | prompt 是否在动工前写；三视角是否真的想过；验收条件是否真的先于实现 |

**AI 不照做时能不能发现？**

- 「没写 prompt」：能发现（如果闸门覆盖）。
- 「写了但事后补」：**不能自动发现**。只能靠：① 文件时间戳/提交顺序（可伪造，且不可靠）；② 另一个模型读 prompt 与 diff，判断验收条件是否被实现牵着走；③ 抽样。
- 当前实际：无。

#### 构建代价与判据

- **新增**：prompt 模板 + 字段检查；成本小。
- **代价**：容易变成填空。`OPEN_ISSUES` E1/E4 已经说明，文档规则一旦不产生红，就会被绕过。
- **反向样本**：
  1. 提交一个非平凡改动但不带 prompt 文件 → 拒绝。
  2. prompt 里验收命令指向不存在的脚本 → `audit-citations --strict` 红。
  3. 「prompt 是事后补的」无法用反向样本证明；只能承认这条闸门只能管形状。

#### 风险

**prompt 模板变成仪式**：作者先写实现，再补一份「老手会漏的步骤」，字段齐全、内容空泛。这个风险在本仓尤其高，因为 PR 模板已经存在但从未被执行——**有模板不等于有流程**。

## 2. 实作

### 2.1 `architect`：先定外框与分工，标准是「无脑照抄也对」

#### 本仓现状

**已存在（强项）**

本仓有多条真正的「单一标准写法」结构闸，这正是 `architect` 想要的「就算无脑照抄，改出来对整个系统也还是对的」：

- `audit-claims` 的 `spec-authority` 探针：`SPEC` 文件数、唯一权威标记、`SPEC_V2.md` 历史归档标记，任一对不上就红；`CLAUDE.md` 明写「禁止新增 `SPEC_*` 文件」。这把「新决策写哪儿」从倡议变成了闸。
- 色板预算：`audit-palette.mjs --strict` 卡世界 ≤24 / UI ≤9 / 并集 ≤32；`palette-budget.test.ts` 对 token 值逐项 deepEqual，换值必红，还禁止一批 render/scenes 文件写裸 `0xRRGGBB`。
- 渲染输入登记：`test/pin-shot-state.test.ts` 的 `unregisteredRenderFields(snapshot)` 与 `missingRenderFields(snapshot)`，新增快照字段没登记进渲染输入表就红。
- 日期长度：`iterations/README.md` 记录了 `memory-day.test.ts` 钉住三处 `DAY_MS` 常量一致，`day-length-prose.test.ts` 钉住散文里的「一天 N 个世界小时」。这是把「同一个长度写了好多遍」收敛成可检查的一致性。
- ADR 字段：`audit-claims` 要求 `status / verified_at / evidence` 合法，证据路径要存在。

**部分存在**

- 这些闸覆盖的是**已经收敛的局部**（色板、渲染输入、SPEC 权威、日期长度），不是「新模块的外框」。
- 没有「新模块必须先写 ADR/架构条目」的检查；`docs/iterations/` 的架构文档是历史资料，不是新代码的入口。
- 反例就在 `OPEN_ISSUES` 里：
  - A3 / B6：`metrics.ts` 与 `synthesizer.ts` 完整、有测试，但生产路径不 import；`fuse.ts` 是生产用的另一套门禁。**两套并行实现，后来者照抄最近的那个文件就可能抄到没接线的那套。**
  - E1：`window.Oracle` 无条件挂载，调试方法与正常游玩路径没有类型隔离；照抄现有浏览器脚本就会继续依赖调试面。
  - B2：`executeCommand` 看起来像执行入口，实际只返回建议；照抄它会绕过 `Simulation.enqueue` 的第二条写世界通道。

这些不是「架构不好」的泛泛而谈，而是**「最近的例子不一定是对的」在本仓的实测证据**。

**完全没有**

- 没有模块注册表/依赖方向检查。
- 没有「新模块没有架构条目就红」的闸。
- 没有「共用底层改动必须走设计评审」的闸。

#### 能否构建

**有条件能。** 条件：

1. 维护 docs/architecture/MODULES.md（建议新增，尚未创建；也可复用 ADR）列出模块、职责、允许的依赖方向、唯一入口。
2. 新增 `world-client/src/<context>/<module>.ts` 时，检查它是否在注册表里；`creator/index.ts` 这类 re-export 入口是否唯一。
3. 对「共用底层」（`simulation.ts`、`save.ts`、`render/`、`server/`）改动，要求 ADR 或设计条目。

**做不到的部分**：无法检查「是不是先定外框再写细节」；也无法自动判断「照抄的最近例子是不是没接线的那套」。后者只能靠注册表把「唯一入口」写死，或靠 review。

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 新模块在注册表里；依赖方向不在禁止列表；共用底层改动有设计条目 | 外框是否真的先于细节；分工是否合理；照抄的例子是否是正确的那个 |

**AI 不照做时能不能发现？**

- 「新模块没登记」：能发现。
- 「照抄了未接线的实现」：**不能自动发现**，除非注册表明确「唯一入口」并在测试里断言生产路径 import 它。本仓 A3/B6 就是现成的反例：测试全绿，但模块没有生产调用方。
- 可发现方式：① 注册表 + 「生产调用方」测试（例如断言 `runAllGateChecks` 有 import）；② 另一个模型审调用图；③ 事后 bug 归因。

#### 构建代价与判据

- **新增**：模块注册表 + 一个「新文件未登记」检查 + 关键模块的「生产调用方」断言。
- **代价**：中。注册表会漂；`OPEN_ISSUES` A3/B6 的删除/接线决策还没拍板（需要用户决策），注册表不能替产品做决定。
- **反向样本**：
  1. 新增一个模块文件（反例可用 world-client/src/world/foo.ts，实际不存在）不登记 → 红。
  2. 在 `render/` 里加第 25 个世界色 → `audit-palette --strict` 红（现成）。
  3. 在快照里加一个渲染字段不登记 → `pin-shot-state.test.ts` 红（现成）。
  4. 把 `metrics.ts` 标成「生产门禁」但没有任何 import → 如果加了「生产调用方」断言，必须红；这条**现在没有**。

#### 风险

**注册表变成第二份文档，且和代码不同步。** 本仓已经有 `docs/WORKTREES.md` 这种「人读约定 + 机器巡检」的成功例子，但也有 `OPEN_ISSUES` E2 的失败模式：判据混在一起后，人开始补账。模块注册表如果只增不减、没有「生产调用方」这种硬断言，就会退化成「新文件加一行」的仪式。

### 2.2 `arena`：同一题目多家模型各自设计，交叉比对、融合亮点

#### 本仓现状

**已存在**

- 没有多模型设计流程。
- 有「文字版备选方案」：`docs/iterations/1027-task-2/` 里有 `architecture-supplement-v0.2.md` 与 `architecture-supplement-v0.2-alt.md`（散文版/替代版），`diagnostics` 也记录过被否掉的写法。这些是**同一作者/同一模型**的备选，不是多家独立设计。
- `docs/INTENT_EXPERIMENT.md` 明确只有 `step-5-preview` 一个模型的数字，并写「换模型必须重跑」。这恰好证明本仓的实验是单模型的，不是 arena。

**部分存在**

- `docs/DECISIONS_20261102.md` 有「选择 / 理由 / 可回退」，是单模型内部的自我比对。
- `docs/GATE_CALIBRATION.md` 有「改前 / 改后」对照，但对照的是同一实现的口径变化，不是两种独立设计。

**完全没有**

- 没有「多个模型各自产出方案」的产物格式。
- 没有「交叉比对 / 融合亮点 / 确认后再实现」的检查。
- 没有记录模型家族/身份的字段。

#### 能否构建

**不能（仓库内作为闸门）。** 仓库可以提供模板和留痕，但不能提供「多家模型独立设计」这个能力本身；也不能验证「独立性」。

**有条件能（作为仓外流程）**：条件是有至少两个不同家族的模型可用，且每个模型的方案独立落盘（不能共享上下文），再由一个第三方模型/人做交叉比对。产物可以放进 `docs/evidence/<task>/arena/`。

#### 是否可强制

**只能靠流程纪律。**

- 工具能检查「arena 目录存在、方案数 ≥2」；不能检查方案是否真的出自不同模型、是否独立、是否被融合。
- **AI 不照做时无法发现**：一个模型可以写两份风格不同的方案，假装两家。可发现方式：① 外部核对模型调用日志；② 抽样让第三家模型判断两份方案是否同源；③ 要求每份方案带模型身份与时间戳（仍可伪造）。
- 当前实际：没有任何留痕，连「假装」都没有。

#### 构建代价与判据

- **新增**：`docs/evidence/<task>/arena/` 目录约定 + 方案模板（候选架构、取舍、失败模式）。
- **代价**：高——时间成本远大于脚本成本；每个任务至少 2–3 份独立设计 + 一次比对。
- **反向样本**：**无法构造「工具挡住违规」的样本**——你可以让一个模型写两份假方案，但没有机械判据能识别同源。这是本文承认的边界：**arena 的「独立性」不可由仓库工具证明**。
- **可做的反向样本（有外部服务时）**：给其中一个候选方案故意埋一个违反 ADR 的缺陷（例如在 `ADR_SAVE.md` 已定的单存档路径之外加第二条写档路径）；交叉比对必须把它标出来。如果融合方案把它带进来，arena 就没有起作用。这不是仓库闸门，是外部流程的有效性测试。
- **可做的弱证明**：要求每份方案附「模型家族 + 会话时间 + 输入 prompt 原文」，由外部核对日志；这不是闸门，是留痕。

#### 风险

**最可能在这一步直接跳过。** 原因：本仓是单人维护、没有第二方，arena 的时间成本又最高；`docs/INTENT_EXPERIMENT.md` 已经暴露「换模型必须重跑」的成本。第二个风险是「融合」变成「选一个最顺眼的」，没有记录被否掉方案的亮点——那样 arena 只剩表演。

### 2.3 TDD 强制：先把对错的测试定死（必然红灯），红灯出现才准写实现

#### 本仓现状

**已存在（测试层很强）**

- `world-client/package.json` 的 `test` 是 `node --import ./test/phaser-hooks.mjs --test test/*.test.ts`；CI 的 `world-client` job 跑 `npm test`，失败就红。
- 测试数量与通过数可用命令取当前值：`cd world-client && npm test` 的汇总行 `# tests / # pass / # fail / # skip`。2026-11-06 的历史读数是 2390 项 / 2381 通过 / 0 失败 / 9 跳过（出处：上一轮本地 `npm test` 汇总行；不代表当前值）。
- 反向用例在测试里大量存在：`render-budget-throttle.test.ts` 的 `(60,58)`、`(60,21)`、`(37,12.5)`、`NaN` 四条必红边界；`behavior-queue.test.ts` 交换规则顺序后结果必须变；`needs-failure.test.ts` 强制饥饿到顶后必须失败；`homecoming.test.ts` 默认世界必须 0 次跨阈。这些是「判据会红」的证据。
- `trace-to-test.ts` 把轨迹转成测试；`docs/BUGS_FOUND.md` 记录 bug 修复与断言在同一个提交里，并写修复前/后读数。

**部分存在**

- 有测试、有 CI，但**没有「测试先于实现」的证据**。当前只能证明「提交时测试是绿的」，不能证明「实现之前测试是红的」。
- `BUGS_FOUND.md` 说「修复代码与断言在同一个提交里」——同一提交不等于先红后绿；它恰好是「AI 先生成实现、再补配合错误逻辑的测试」无法排除的形态。
- 测试本身可能写错：本仓已有 `docs/OPEN_ISSUES.md` A1 的例子——`schemaPassRate` 恒为 1、`manualModificationRate` 恒为 0，因为被拒尝试从不记账。测试可能全绿，但分母是假的。

**完全没有**

- 没有 red-first 闸。
- 没有「测试必须在 base 上失败」的检查。
- 没有「新增测试是否只是复述现有实现」的检查。

#### 能否构建

**能。** 这是四阶段里最适合用工具强制的一条。条件：

1. 在 PR/合并前，取 merge-base 与当前分支的 diff，把 **只含 `world-client/test/**` 的改动**应用到 base 上。
2. 运行被改动的测试文件（或全量 `npm test`），**必须非零退出**。
3. 只有出现红灯后，才允许把实现 diff 一起合入。

这条闸的判据是「测试在 base 上必须红」，不是「测试在分支上必须绿」——后者 `npm test` 已经做了。

**边界条件**（必须写清，否则会变成假红）：

- **纯重构/回归测试**：新增测试可能本来就在 base 上绿（例如重构前后行为相同）。这类应显式登记 `Red-First: exempt` 并写明理由，不能悄悄放行。
- **测试依赖新类型/新导出**：在 base 上会编译失败，也算红；但 TypeScript 的类型剥离与 import 失败要能被正确识别为「红」而不是「脚本坏了」。
- **flaky 测试**：base 上的红可能是 flaky，不是「新测试真的抓到了缺失」。需要重跑或标注。
- **删除测试**：闸门不能只数「新测试红」；还要防「删掉旧测试让全绿」。

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 新增/改动的测试在 base 上红；实现后转绿；删除测试会被发现 | 测试是否真的表达了需求；测试是否只是配合错误实现；红是因为缺功能还是因为测试写错 |

**AI 不照做时能不能发现？**

- 「没写测试就写实现」：能发现（如果 diff 里没有测试改动，闸门红）。
- 「先写实现再补一个在 base 上也绿的测试」：**能发现**——闸门要求 base 红，绿就红。
- 「测试写错，但红灯确实出现了」：**不能自动发现**。这是 TDD 闸的固有边界：它能防「假测试」，不能防「错需求」。错需求要靠验收阶段的真实用户路径与外部核对。
- 当前实际：没有这条闸，所以以上都发现不了。

#### 构建代价与判据

- **新增**：world-client/scripts/red-first.mjs（建议新增）+ 一个 CI job（或在本地合并脚本里跑）。
- **代价**：中到高。需要处理 base checkout、依赖安装、测试选择、超时；CI 时间会增加。若每次全量 `npm test` 约数分钟，成本可接受，但共享 runner 的 flaky 风险要算进去（`docs/OPEN_ISSUES.md` E3 已经记录共享 runner 比本地慢一个量级）。
- **反向样本**：
  1. 故意加一个「断言当前行为」的测试（在 base 上本来就绿）→ red-first job 必须红。
  2. 故意只改实现、不改测试 → red-first job 必须红。
  3. 故意删掉一个旧测试 → 需要一个「测试数量/用例名不得减少」的检查；否则这条反向样本不成立。
  4. 故意写一个在 base 上因 import 失败而红的测试 → 必须被识别为「红」，不是脚本错误。

#### 风险

**最可能半途而废的是「假红太多，闸门被关掉」。** 本仓的测试不是纯函数集合：大量用例需要 Phaser hook、服务端、固定时钟；base checkout 后只套测试 diff，可能因为缺少实现导出而报「模块不存在」，与「断言失败」混在一起。维护者一旦发现红得莫名其妙，就会加白名单，最后白名单比闸门长。第二个风险是「只对新增测试生效」，重构与修 bug 的测试被豁免，闸门覆盖不到最容易造假的那一类。

## 3. 验收

### 3.1 `create-verification`：写一份像真人一样操作并检查 APP 的 SOP，录视频/截图作证据

#### 本仓现状

**已存在（强项，但形状不完全对）**

- `docs/evidence/VERIFIABLE_FLOWS.md` 把 10 条流程写成「触发命令 + 判据 + 反向用例 + 产物落点」，并明确 `verify-all.mjs` 是人工入口：不得接 CI、不得挂进 `npm test`、不得作为合并闸门。
- 浏览器闸门真实存在：`smoke.mjs`、`check-phases.mjs`、`check-persistence.mjs`、`check-render-budget.mjs`、`check-dengchao.mjs`。
- 2026-11-06 的 Phaser 4 证据有五道浏览器的读数：`smoke` 132 项、`phases` 34 项、`persistence` 8 项、`render-budget` 6 项 ×2 轮、`setting` 29 项（`docs/evidence/phaser4-upgrade/README.md`）。
- 截图与逐像素判据：`screens-diff.py` 的三层差（精确/可见/结构块）、`verify-screens-diff-selfcheck.py` 的绿例与必红例、钉子契约的三档 0.0000%。

**部分存在**

- **不是「真人操作路径」**：浏览器闸门大量依赖 `window.Oracle` 的调试方法（`pinShotState` / `pinActors` / `pinTrails` / `debugSetWeather` 等）。`docs/OPEN_ISSUES.md` E1 明确说这些方法与正常游玩路径没有类型隔离，生产也可达。照这套 SOP 点一遍，验的是「调试面 + 世界状态」，不是「玩家点按钮」。
- **CI 只跑三道浏览器闸门**：`persistence` / `render-budget` / `phases`；`smoke` 与 `setting` 不在 CI。CI 的 `EVAL_OUT` 指向 `runner.temp`，跑完只检查工作区是否干净，**没有 `upload-artifact`**——截图不留在证据里。
- **没有视频**：全仓没有视频录制脚本；截图是 PNG，不是「录一段真实用户路径」。
- **DOM 层缺口**：`docs/evidence/VERIFIABLE_FLOWS.md` 流程 8 记录 `test:buttons` 因 `/api/memory/list` 回 404 退出 2，镇志抽屉点不到。
- **截图基线本身不稳**：`docs/evidence/SCREENS_CAPTURE_GATE.md` 记录同一 HEAD 两跑，`01-salute` 可见差 24.765%、`03-deliver` 1.128%，原因是环境染色档位与烟柱粒子相位；该文档的结论是「第 0 步自证未通过」，没有重录基线。这说明「截图全等」在某些流程上还不是稳定判据。

**完全没有**

- 没有一份「真实用户从打开页面到完成一条完整任务」的 SOP。
- 没有持久化的截图/视频证据链（CI 临时目录不算）。
- 没有「每次改完按真实用户路径点一遍」的强制流程。

#### 能否构建

**能。** 条件：

1. 写一份真实用户路径 SOP（建议放在 docs/evidence/SOP_BROWSER_WALKTHROUGH.md，尚未创建）：从首页加载、点 HUD、开镇志抽屉、发一句指令、看回执、刷新、读档，每一步写可见结果与判据。
2. 用 Playwright 走真实 DOM 点击，不调用 `window.Oracle`（或只在只读断言里调用）；脚本退出码即判据。
3. CI 用 `upload-artifact` 保留截图/视频，作为每次运行的证据。
4. 对「必须看到什么」写显式断言（例如抽屉打开后出现某段文字、指令后建筑数 +1、刷新后等级不丢）。

**做不到的部分**：脚本能证明「页面长这样」，不能证明「人真的看懂了好不好」。主观观感与手感仍然只能靠人。

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 真实用户路径脚本能跑、会红；截图/视频作为 artifact 留存；DOM 断言逐条可查 | 「每次改完都点一遍」；「人真的看了截图」；「观感对不对」 |

**AI 不照做时能不能发现？**

- 「没跑 SOP」：如果 SOP 接进 CI/合并前，能发现。
- 「跑了但没看」：**不能自动发现**；artifact 只能证明「跑过」，不能证明「看过」。可发现方式：① 要求把截图链接贴进 PR/交付说明（留痕）；② 抽样由另一个模型读截图与断言；③ 外部核对。
- 当前实际：SOP 没有，artifact 没有，连「跑过」都只在本地，不在 CI。

#### 构建代价与判据

- **新增**：一份 SOP + 一个真实用户路径脚本 + CI artifact 上传；可能还要修 `test:buttons` 的 404（服务端 `/api/memory/list`）。
- **代价**：中。主要成本在「不依赖 Oracle 的稳定选择器」与 CI 运行时；本仓的浏览器闸门已经因为墙钟判据脆（E3）吃过红，真实用户脚本更容易受时序影响。
- **反向样本**：
  1. 故意把镇志按钮绑到一个坏 handler → SOP 必须红。
  2. 故意让 `/api/memory/list` 回 404 → 抽屉步骤必须红（这正是当前 `test:buttons` 的状态）。
  3. 故意把刷新后的等级清空 → SOP 的「刷新后等级不丢」步骤必须红（对应 `OPEN_ISSUES` A2 的已知问题）。
  4. 反向样本 2 现在就是红的，**不能当绿**；它证明的是「脚本能发现」，不是「功能已修」。

#### 风险

**最可能半途而废在「脚本依赖调试接口」这一步。** 本仓现成的浏览器闸门全部经 `window.Oracle` 取状态（E1），改真实用户路径等于重写选择器与状态读取；而 `OPEN_ISSUES` E1 又指出「任何一项改动都会影响全部既有浏览器脚本与证据链」，所以最省力的路径是继续用 Oracle——那就退回「验调试面，不验玩家路径」。第二个风险是 CI artifact 没人看，视频/截图变成「传上去就忘」。

### 3.2 `blast radius`：给每张 PR 标风险高低

#### 本仓现状

**已存在（只有路径点名）**

- `.github/pull_request_template.md` 的「改了什么」栏要求「涉及 `render/`、`save.ts`、`server/` 时点名对应路径」。
- `.github/CODEOWNERS` 按路径分组：`world-client/src/render/`、`world-client/src/world/save.ts`、`server/`、`.githooks/`、`.github/`、`docs/`。但每一组都是 `@cs1lion`——**同一个人**。
- `docs/OPEN_ISSUES.md` 的每条都点名路径与影响范围，可作为「哪些区域危险」的现成清单。

**部分存在**

- 有路径意识，没有风险等级。
- 有 CODEOWNERS，没有 required review（远端分支保护不可用，见 `CLAUDE.md` 的「权限边界」一节）。
- PR 模板没有 `Blast-Radius:` 字段。

**完全没有**

- 没有风险分类器。
- 没有「高风险改动必须细看」的闸。
- 没有「低风险改动可扫一眼」的分流。

#### 能否构建

**能。** 条件：

1. 定义路径清单：`world-client/src/world/simulation.ts`、`save.ts`、`world-client/src/render/`、`server/`、`world-client/scripts/audit-*`、`.githooks/` 等为高风险；`docs/`、`eval/`、部分 `test/` 为低风险。
2. pre-push 或合并脚本读 diff，计算风险等级，要求提交带 `Blast-Radius: high|low`；高风险必须带 `Reviewed-By:`（且与作者不同）。
3. 低风险改动不要求 review，但要留 `Blast-Radius: low` 的痕迹，供事后抽样。

**做不到的部分**：风险等级是清单决定的，清单漏了某个共用底层，闸门就会把高风险当低风险。**清单本身要靠 review 维护。**

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 路径命中高风险清单时必须有标记；高风险必须有外部 reviewer 标记；标记与实际路径一致 | 「细看」是否真的发生；reviewer 是否真的读了 diff；风险等级是否被故意标低 |

**AI 不照做时能不能发现？**

- 「没标」：能发现。
- 「标低」：如果清单覆盖该路径，能发现（脚本按实际路径算，不只看作者声明）。
- 「reviewer 标记是假的」：**不能自动发现**；只能靠 `Reviewed-By:` 对应的人/模型确认，或抽样外部核对。
- 当前实际：清单没有、标记没有、reviewer 没有。

#### 构建代价与判据

- **新增**：一个路径风险表 + 一个 diff 分类脚本 + pre-push/合并脚本里的 trailer 检查。
- **代价**：小到中。`git diff --name-only` 就能算；不需要新依赖。
- **反向样本**：
  1. 改 `world-client/src/world/save.ts` 但标 `Blast-Radius: low` → 必须被拒。
  2. 改 `docs/` 标 `high` → 允许，但记录；证明闸门不是「一律加严」到没人用。
  3. 高风险改动没有 `Reviewed-By:` → 必须被拒（前提是 review 闸真的存在）。
  4. **当前 `PWE_ALLOW_PUSH_MAIN=1` 会在 `pre-push` 开头直接 `exit 0`**（`.githooks/pre-push`），反向样本 1/3 会被豁免绕过——这是这条闸门能不能成立的关键条件。

#### 风险

**最可能半途而废在「豁免 push」这一步。** 本仓的 pre-push 保护在 `PWE_ALLOW_PUSH_MAIN=1` 时整条跳过（不只是跳过 main 保护），而实际交付又常用这个豁免。只要豁免还在，blast radius 和 review 都只能在「愿意遵守」的时候生效。第二个风险是路径清单漂移：`OPEN_ISSUES` E1 已经说明 `SandboxScene.ts` 同时是渲染、调试、状态写入，单一分类很难准确。

### 3.3 `interrogate`：同一份代码丢给不同家族的模型互审

#### 本仓现状

**已存在**

- 有「自我审查」的痕迹：`docs/OPEN_ISSUES.md` 的 `[事实]` / `[推断]` 分栏；`docs/DOC_GOVERNANCE_REPORT.md` 记录 ADR 的 `status` 由 AI 只填 `pending-review`；`docs/adr/` 当前全部标 `aligned`（2026-11-06 本地 `audit-claims` 读数 files=10 valid=10；份数以命令为准）。
- 有「另一个视角」的雏形：`AGENT_TRUST_AND_VERIFIABILITY.md` 把文档自己承认的边界写出来；`OPEN_ISSUES` 的 D/E/F 是作者自己登记的风险。

**部分存在**

- 这些都是**同一模型/同一作者**的自我审查；不是不同家族。
- `DOC_GOVERNANCE_REPORT.md` 提到 ADR 需要人签字，但本仓只有一位维护者；「人」和「AI」不是两个独立评审方。
- 没有 PR review 记录。

**完全没有**

- 没有跨模型/跨家族的审查产物。
- 没有「同一模型换角色扮演」的记录，也没有防止这种伪装的字段。

#### 能否构建

**不能（仓库内作为闸门）。** 仓库可以提供 review 模板与留痕字段，但不能提供「不同家族的模型」这个能力，也不能验证独立性。

**有条件能（作为仓外流程）**：条件是有另一个模型家族可用；审查结果落 `docs/evidence/<task>/REVIEW.md`，写模型家族、审查范围、发现的问题、是否修复。

#### 是否可强制

**只能靠流程纪律。**

- 工具能检查 `docs/evidence/<task>/REVIEW.md` 存在、字段非空；不能检查审查者真的不同家族、真的读了代码。
- **AI 不照做时无法发现**。可发现方式：① 外部核对模型调用日志；② 抽样让第三家模型判断 review 是否只复述了 diff；③ 用「review 是否发现了实现者没发现的问题」作为事后指标——但这仍是统计，不是闸门。
- 当前实际：没有 `docs/evidence/<task>/REVIEW.md`，也没有 review 流程。

#### 构建代价与判据

- **新增**：`docs/evidence/<task>/REVIEW.md` 模板 + 审查范围清单（至少覆盖高风险路径）。
- **代价**：中到高（时间成本）；脚本成本低。
- **反向样本**：**无法构造「工具挡住违规」的样本**。你可以让同一模型换角色写一份 review，工具无法识别。这是本文承认的边界。
- **可做的反向样本（有外部模型时）**：把 `docs/BUGS_FOUND.md` 里已经修复的一个 bug 重新注入 diff（不告诉 reviewer 是哪一个），跨家族 reviewer 必须指出来。如果指不出来，说明 review 只是复述，不是独立审查。这是外部流程的有效性测试，不是仓库闸门。
- **可做的弱证明**：要求 review 里至少列一条「实现者没写进决策表的失败尝试」；如果一条都没有，抽样的第三方可以怀疑 review 没读代码。这不是闸门。

#### 风险

**最可能半途而废在「同一模型换角色扮演」这一步。** 方法论自己已经指出：同一模型换角色扮演，盲点不变。本仓只有一位维护者，如果没有外部模型，interrogate 很容易退化成「让 AI 再读一遍自己的 diff」，然后写一份看起来很全面的 review。第二个风险是 review 变成「只挑格式」，因为真正的架构问题（A3/B6/E1）需要读调用图，成本高。

## 4. 加固

### 4.1 铁律：写 PR 的 AI 无权核准自己的 PR

#### 本仓现状

**已存在（有文件，但没有进入执行）**

- `.github/CODEOWNERS` 按路径指定 reviewer，但所有路径都是 `@cs1lion`。
- `.github/pull_request_template.md` 要求「改了什么 / 为什么 / 验证命令与读数」。
- `.githooks/pre-push` 拒绝任何以 `refs/heads/main` 为目标的 push；`scripts/check-hooks.mjs` 把「钩子是否安装」变成可跑、可红的读数；CI 的 `repo-harness` job 会先读一次未安装状态，再安装并复核。
- `CLAUDE.md` 的「权限边界」写明：远端分支保护 API 当前返回 404，所以把 main 的直推边界放在本地。

**部分存在**

- 保护只覆盖「直推 main」，不覆盖「作者自己合并自己的分支」。本仓的实际合并是本地 `--no-ff` 合 main，然后 `PWE_ALLOW_PUSH_MAIN=1` push；`git log --merges` 里没有 PR 号。**作者、合并者、推送者是同一个人/同一个 AI。**
- `CODEOWNERS` 只有走 PR 才触发；没有 PR，它等于没写。
- `pre-push` 的 `PWE_ALLOW_PUSH_MAIN=1` 在脚本开头直接 `exit 0`，**整条 pre-push 被跳过**（不只是 main 保护）。这意味着一旦用豁免，blast radius、review trailer 等所有未来加在 pre-push 的检查也一起失效。
- 本文这次交付也是同一模式：分支 → 本地 `--no-ff` 合 main → `PWE_ALLOW_PUSH_MAIN=1` push；没有 PR，作者/合并者/推送者是同一个 AI。**这不是假设，是本次交付的实际流程。**

**完全没有**

- 没有「作者 ≠ 核准者」的强制。
- 没有 required review、没有 required status checks（远端保护不可用）。
- 没有独立的 merge gate 脚本。

#### 能否构建

**有条件能。** 两个条件，二选一或同时：

1. **远端条件**：恢复 GitHub 分支保护/规则集权限，要求 PR + 至少 1 个非作者 approval + 状态检查通过。当前 `CLAUDE.md` 记录该 API 返回 404，所以这个条件现在不成立。
2. **本地条件**：新增 scripts/merge-gate.mjs（建议新增），在 `--no-ff` 合并前检查：源分支 tip 有 `Reviewed-By:` trailer，且 reviewer 的模型家族/身份与作者不同；CI 对该 sha 通过；否则拒绝合并。同时把 `PWE_ALLOW_PUSH_MAIN=1` 的语义收窄到「只跳过直推 main 检查」，不跳过 review trailer 检查。

**做不到的部分**：本地 gate 仍可被 `--no-verify` 或手工 `git merge` 绕过；它只能提高「误操作被发现」的概率，不是物理强制。**真正的物理强制只能来自远端分支保护。**

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 本地合并脚本要求 `Reviewed-By:` 且非作者；远端 PR approval（若权限恢复） | reviewer 是否真的读了；是否真的独立；reviewer 标记是否被伪造 |

**AI 不照做时能不能发现？**

- 「没 review 就合并」：如果走本地 merge gate，能发现；如果直接 `git merge` + 豁免 push，**不能发现**。
- 「reviewer 是同一个 AI 换角色」：**不能自动发现**；只能靠模型家族字段 + 外部核对调用日志。
- 当前实际：没有本地 merge gate，也没有 PR；**只能靠事后读 `git log` 发现「没有 review 痕迹」**（本轮就是这么发现的：合并提交没有 PR 号，也没有 `Reviewed-By`）。

#### 构建代价与判据

- **新增**：本地 merge gate（小）或远端分支保护（需要权限/套餐，成本取决于账号）；`Reviewed-By:` trailer 约定。
- **代价**：本地 gate 小；远端条件目前不成立，属于外部依赖。
- **反向样本**：
  1. 作者自己写、自己合并、带 `Reviewed-By:` = 作者 → 本地 merge gate 必须拒绝。
  2. reviewer 标记为空或指向不存在的身份 → 拒绝。
  3. 用 `PWE_ALLOW_PUSH_MAIN=1` 推送一个没有 review 的 main → 必须仍然拒绝（前提是豁免语义被收窄；当前会直接跳过）。
  4. 反向样本 3 是**当前失败**的：豁免在脚本开头 `exit 0`，这条闸门现在不存在。

#### 风险

**最可能半途而废在「灾难恢复豁免变成日常路径」。** 本仓的实际交付已经证明这一点：`--no-ff` 合 main + `PWE_ALLOW_PUSH_MAIN=1` 是常规操作，不是灾难恢复。只要这条路径存在，作者自批就无法被挡。第二个风险是「reviewer」只有一个人，CODEOWNERS 全指向 `@cs1lion`；即使走 PR，也只是「自己批自己」。

### 4.2 `swarm`：约 10 个全程没参与写码的独立 AI 在云端同时打开 APP 到处点

#### 本仓现状

**完全没有**

- 没有云端多 agent 编排。
- 没有「10 个独立 AI 同时打开 APP」的脚本或服务。
- 没有「全票通过才自动合并」的合并闸。
- 现有浏览器闸门是单进程、单浏览器、固定路径（`smoke` / `phases` / `persistence` / `render-budget` / `setting`），不是自由探索。

**部分存在**

- `docs/evidence/VERIFIABLE_FLOWS.md` 的流程总表可以作为「每个 agent 该点哪些路径」的输入；`verify-all.mjs` 可以当单 agent 的入口。但这些都不是 swarm。

#### 能否构建

**不能（仓库内）。** 需要外部云浏览器/agent 编排服务、并发配额、结果聚合与合并闸；本仓没有这些基础设施。

**有条件能（仓外）**：条件是有 10 个独立会话/浏览器、每个会话不共享上下文、结果落盘、全票通过才允许合并。仓库只能提供「要检查什么」的 SOP 和「结果怎么汇总」的格式。

#### 是否可强制

**只能靠流程纪律 + 外部服务。**

- 工具能检查「有 10 份结果文件、全部 pass」；不能检查这 10 个 agent 是否真的独立、是否真的没参与写码、是否真的到处点。
- **AI 不照做时无法发现**：可以复制同一份结果 10 次。可发现方式：① 外部服务的会话日志；② 结果里带不同的随机探索路径与截图哈希；③ 抽样由人看差异。
- 当前实际：没有。

#### 构建代价与判据

- **新增**：云 agent 编排、结果聚合脚本、全票合并闸。
- **代价**：高。10 路并发浏览器的成本、稳定性、结果去重都不便宜；本仓 CI 的浏览器 job 已经因为共享 runner 的墙钟问题红过（`GATE_CALIBRATION` 第八节、`OPEN_ISSUES` E3）。
- **反向样本**：如果建成，可以让 1 个 agent 故意走坏路径（例如点镇志抽屉），其余 9 个 pass → 全票不通过，合并被拒。这个反向样本可构造，但前提是 swarm 本身存在。
- **当前**：连正向的 10 份结果都没有。

#### 风险

**这是整套方法论在本仓最可能完全建不起来的一步。** 原因不是技术难，而是「10 个全程没参与写码的独立 AI」需要第二方/多方，而本仓只有一位维护者、没有 PR 流程、没有云端 agent 基础设施。第二个风险是成本：10 路浏览器在共享 runner 上会放大 E3 的墙钟脆弱性，结果可能是「全票不通过」但原因是机器慢，不是代码坏。

### 4.3 `show me your work`：边做边填决策记录表，第二天由另一家模型核对

#### 本仓现状

**已存在（强项，但是分块级，不是 PR 级）**

- `docs/evidence/PROGRESS.md` 每个块都有「改了什么结构」「指纹对照」「闸门」「真问题」「被否掉的写法及原因」「阻塞」「证据」。这几乎是决策记录表的雏形。
- `docs/DECISIONS_20261102.md` 记录岔路的选择、理由、可回退，以及「待用户复核」。
- `docs/BUGS_FOUND.md` 记录修复前/后读数、影响范围，而不是只写「已修」。
- `docs/evidence/INDEX.md` 每条证据都有日期、关键读数、来源。
- 各 `docs/evidence/<topic>/README.md` 记录命令、读数、失败与边界。

**部分存在**

- 这些是**按块/按主题**的记录，不是每张 PR/每次改动都填。
- 没有统一的「试过什么写法失败 / 最后为什么这么改 / 怎么验证」三列表格；`PROGRESS` 有「被否掉的写法」，但不是每次都写「怎么验证」。
- 没有「另派一家模型的 AI 核对这张表」的流程；`AGENT_TRUST_AND_VERIFIABILITY.md` 是自己承认边界的文档，但核对者还是同一作者。

**完全没有**

- 没有决策表的 schema/字段检查。
- 没有第二方核对记录。

#### 能否构建

**有条件能。** 条件：

1. 定义 `docs/evidence/<task>/DECISIONS.md` 模板，至少四列：试过的写法 / 为什么失败 / 最后为什么这么改 / 怎么验证（命令 + 读数 + 反向样本）。
2. 对高风险路径的改动，合并前检查该文件存在且四列非空。
3. 第二方核对仍是仓外流程：由另一家模型读表 + diff，标出「验证不扎实 / 有风险」的地方；结果落 `docs/evidence/<task>/REVIEW.md`。

**做不到的部分**：字段可以填满，内容可以空泛；「试过什么失败」最常见的是省略。工具无法判断真实性。

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 决策表存在；四列非空；验证命令存在 | 「失败尝试」是否真的发生过；「为什么这么改」是否是真原因；第二方是否真的核对了 |

**AI 不照做时能不能发现？**

- 「没填表」：能发现。
- 「填了但只写成功路径」：**不能自动发现**。可发现方式：① 第二方模型读表，追问「为什么没有失败尝试」；② 抽查验证命令是否真的能复现读数；③ 事后 bug 归因——如果一次改动失败但表里没有记录，说明表没被边做边填。
- 当前实际：`PROGRESS` 有分块记录，但没有「第二方核对」；`AGENT_TRUST_AND_VERIFIABILITY.md` 的自我坦白是好的开始，但它不是独立核对。

#### 构建代价与判据

- **新增**：决策表模板 + 字段检查 + `docs/evidence/<task>/REVIEW.md` 约定。
- **代价**：小到中。模板成本低；第二方核对需要外部模型与时间。
- **反向样本**：
  1. 提交一个高风险改动，`docs/evidence/<task>/DECISIONS.md` 只有一行「按方案实现」→ 字段检查必须红。
  2. 验证列写一个不存在的命令 → `audit-citations` 或命令存在性检查红。
  3. 「失败尝试」为空 → 如果模板要求至少一条，红；否则需要第二方追问。
  4. 「第二方核对」无法用反向样本证明；只能承认。

#### 风险

**最可能半途而废在「只写成功路径」。** 本仓 `PROGRESS.md` 已经证明「被否掉的写法」是可以写出来的，但它靠的是作者自觉；一旦变成必填字段，最省力的填法是「没有别的做法」。第二个风险是第二方核对没有第二方——`OPEN_ISSUES` 的 D/E/F 已经等了用户决策，说明「等别人核对」在本仓经常变成「等不到」。

### 4.4 `correct`：出错不要加 prompt 说「下次注意」，要改环境让错物理上不可能

#### 本仓现状

**已存在（强项，有真实的结构性修复）**

- `audit-references.ts`：带行号的引用必须指到真实文件、行号在范围内、那段有可落脚内容；`audit-citations.ts`：不带行号的路径 token 必须对应真实文件；`audit-sections.ts`：点名的节号必须存在；`audit-claims.ts`：文档里的数字断言按固定探针复算，ADR 字段校验。
- `palette-budget.test.ts`：token 值逐项 deepEqual，换值必红；禁止裸 `0xRRGGBB`。
- `pin-shot-state.test.ts` 的 `unregisteredRenderFields` / `missingRenderFields`：新增快照字段不登记就红。
- `worktrees-audit.mjs`：未登记/过期/表项悬空可 `--strict` 红。
- `.githooks/pre-push` + `check-hooks.mjs`：main 直推保护 + 钩子安装自检。
- `iterations/README.md` 记录的 `memory-day.test.ts` / `day-length-prose.test.ts`：把「一天 = 24 个世界小时」从散文约定变成一致性断言。

这些正是「把教训做成结构」的形状：不是写「请注意」，而是让错误直接红。

**部分存在**

- 本仓同时有大量只写在 markdown 的规则，而且**没有检测**：
  - 端口纪律「5188 / 5191 / 5202 / 5203 一律不用」写在 `docs/evidence/VERIFIABLE_FLOWS.md` 第 0 节，`docs/RESUME.md` 另有「不指定端口就打 5188、曾造成两次假红」的记录；但 `smoke.mjs`、四个抓拍脚本、`check-render-budget.mjs` 的默认端口仍落在 5188 / 5202（`VERIFIABLE_FLOWS.md` 第 0 节已列）；没有脚本检查「这次是不是用了禁用端口」。
  - 「不 `stash`、不丢弃、不动别人工作树」是本次交付说明的边界；`docs/RESUME.md` 反而建议中断实验用 `git stash push` 并把 stash 名写进断点记录。两条规则互相冲突，且都没有闸门——这本身就是「只能靠纪律」的证据。
  - `verify-all.mjs` 不得接 CI / `npm test`，这条是 `VERIFIABLE_FLOWS.md` 的定位声明；没有脚本检查「有人把它接进去」。当然，这条本身是「不要自动化」的规则，不适合做闸门。
  - `worktrees:audit` 在 CI 里跑的是非 strict（`.github/workflows/ci.yml` 的 `repo-harness` job），本地 strict 才会红；「未登记」在 CI 不会红。
  - 「易变测量值不写死进正文」是最近两轮文档的口径（`AGENT_TRUST_AND_VERIFIABILITY.md` / `VERIFIABLE_FLOWS.md` 开头），没有 linter；只能靠作者遵守。
- `audit-claims` 只覆盖少量已知断言与 ADR 字段（2026-11-06 本地读数：markers=6、adr-schema files=10 valid=10；跑 `node scripts/audit-claims.ts --strict` 取当前值）；`docs/DOC_GOVERNANCE_REPORT.md` 也记录过「误报率待观察」。它不是一个通用的「文档数字」闸。

**完全没有**

- 没有「教训 → 规则」的登记表（哪条事故变成了哪个测试/lint/CI job）。
- 没有「这条规则只能靠纪律」的显式标注与抽样方案。
- 没有对「AI 没照做」的检测；markdown 规则不产生红。

#### 能否构建

**能（一部分）。** 条件：

1. 建一份教训登记表（建议放在 docs/evidence/LESSONS.md，尚未创建），每条教训写：事故/证据 / 结构性修复（测试、lint、CI job、脚本）/ 如果只能纪律，写「怎么发现」（抽样、留痕、外部核对）。
2. 对能结构化的规则，直接加测试或 CI：例如端口默认值改成可配置并禁止禁用端口；`worktrees:audit --strict` 进 CI（但要先拆 E2 的退出码语义）；文档数字改用命令/日期口径（可由 `prose-numbers.ts` 或新 lint 检查）。
3. 对不能结构化的规则，明确标 `discipline-only`，并配一个抽样方案（例如每次合并随机抽一条规则，人工/外部模型核对）。

**做不到的部分**：不是所有教训都能变成物理不可能。主观判断、架构取舍、多模型独立性，仍然只能靠流程。

#### 是否可强制

| 可强制 | 只能靠纪律 |
| --- | --- |
| 引用/节号/色板/渲染输入/账本字段/日期长度；可加端口、strict worktree、文档数字 lint | 「先读后规划」「多想一个备选」「review 是否认真」「模型是否独立」「观感是否好」 |

**AI 不照做时能不能发现？**

- 能结构化的：能发现，且会红。
- 只能纪律的：**不能发现**。可发现方式：留痕（决策表、review 记录、截图）、抽样（随机抽一条规则核对）、外部核对（另一家模型/人）。**如果这三样都没有，就是「不知道」。**
- 当前实际：本仓有 5 条以上「只写在 markdown」的规则，且没有抽样；这正是 `correct` 在本仓最大的缺口。

#### 构建代价与判据

- **新增**：LESSONS.md 登记表（建议新增）+ 每条教训的「结构/纪律」分类 + 抽样方案。
- **代价**：低到中。加一两条 lint/CI 便宜；难的是「持续把新事故归位」。
- **反向样本**：
  1. 故意在 `render/` 写裸 `0xRRGGBB` → `palette-budget.test.ts` 红（现成）。
  2. 故意加一个未登记的渲染字段 → `pin-shot-state.test.ts` 红（现成）。
  3. 故意在 `index.html` 加第 10 个 UI hex → `audit-palette --strict` 退出 1（文档记录过，但本轮只读约束下未执行；`VERIFIABLE_FLOWS.md` 流程 6 明确标「第 10 色红例未执行」）。
  4. 故意用禁用端口起服务 → **当前没有任何闸门会红**；这条反例证明「端口纪律只是纪律」。
  5. 故意新建 worktree 不登记 → 本地 `--strict` 红，但 CI 非 strict 不红；这条反例证明「同一规则在不同入口强度不同」。
  6. 故意写一个会变的历史数字 → 没有 lint；只能靠 review。这是最近两轮文档修复的动机（`docs/evidence/INDEX.md` 记录了 2026-11-06 的 22 处未解析引用 + 5 处行号存疑）。

#### 风险

**最可能半途而废在「把 markdown 当成已经建成了」。** 本仓已经有大量这种证据：端口纪律、`verify-all` 不接 CI、`worktrees:audit --strict`、易变数字口径、不 `stash`——这些都写在文档里，但只有一部分有闸。第二个风险是「结构化的成本被低估」：把一条规则变成 lint 要处理误报，而误报会让人关掉闸门；`audit-citations.ts` 的注释自己记录了「一条只产误报、不产真阳的判据比没有更糟」。

## 5. 如果真要建，建议的顺序与最小集合

不建议一次把四阶段 + 加固全建。按「能强制、便宜、反向样本现成」排序：

| 顺序 | 建什么 | 为什么先建它 | 反向样本 |
| --- | --- | --- | --- |
| 1 | `blast radius` 路径分类 + trailer | 便宜，`git diff --name-only` 就够；能直接挡住共用底层改动被当成低风险 | save.ts 标 low → 拒绝 |
| 2 | `red-first` CI job | 能真正挡住「先实现后补假测试」，是 TDD 的核心闸 | base 上测试绿 → 红 |
| 3 | 浏览器 SOP + artifact 上传 | 已有五道浏览器闸门与截图判据，补「真实用户路径 + 留证」成本最低 | 点坏按钮 → 红；artifact 留存 |
| 4 | `show me your work` 决策表字段检查 | 本仓 `PROGRESS` 已有雏形，补字段与第二方核对 | 决策表缺列 → 红 |
| 5 | 本地 merge gate + 收窄豁免 | 需要先决定「是否继续用豁免 push」；不解决这条，前四条都能被绕过 | 作者自批 → 拒绝 |
| 6 | `arena` / `swarm` / `interrogate` | 成本最高、最依赖第二方；没有外部模型/服务就建不起来 | 不可构造可信反向样本 |

**最小可用集合**（如果只建一半）：1 + 2 + 3 + 5。它们能覆盖「结果可复算」之外的三个最贵的失败模式：共用底层被轻看、假测试、作者自批。4 与 6 属于「有则更好」，没有也不至于让前四条失效。

## 6. 结论

1. **规划阶段的 `how` / `why` 有条件能**：本仓有阅读指引、ADR、决策记录、引用审计，但没有「计划产物 + 历史链接」的闸。能强制的是「文档存在、引用存在」，不能强制「读透、挖对」。
2. **`sharpen` 只能靠流程纪律**：PR 模板有验证读数栏，但没有 prompt/验收条件产物，且模板本身没有执行。留痕可抽查，质量无法判。
3. **实作阶段的 `architect` 有条件能**：本仓已有色板、渲染输入、SPEC 权威、日期长度等「单一标准写法」结构闸；但新模块外框、调用图、唯一入口没有闸。`OPEN_ISSUES` A3/B6/E1 是「最近的例子不一定对」的现成证据。
4. **`arena` 不能（仓库内）**：没有多模型流程，只有单模型实验与文字备选。独立性不可由仓库工具证明。
5. **TDD 能**：这是最适合工具强制的一条。用「base 上只套测试 diff 必须红」的 job，可以真正挡住假测试；边界是纯重构、flaky、删测试。
6. **验收阶段 `create-verification` 能**：本仓已有流程总表、五道浏览器读数（2026-11-06）、截图判据；缺真实用户路径、artifact 留存、DOM 层。`SCREENS_CAPTURE_GATE` 已经暴露截图基线不稳（`01-salute` 24.765%）。
7. **`blast radius` 能**：路径分类 + trailer 便宜且有效；但 `PWE_ALLOW_PUSH_MAIN=1` 会整条跳过 pre-push，必须先收窄豁免。
8. **`interrogate` 不能（仓库内）**：没有跨家族 review；同一模型换角色无法被工具识别。
9. **加固阶段的「作者不自批」有条件能**：远端分支保护当前 404，本地只有「拦直推 main」，不拦「作者自己合并自己的分支」；实际交付路径正是本地合并 + 豁免 push，`git log` 里没有 PR 号。
10. **`swarm` 不能（仓库内）**：没有云端多 agent 基础设施；10 路浏览器还会放大共享 runner 的墙钟脆弱性（E3）。
11. **`show me your work` 有条件能**：`PROGRESS` / `DECISIONS` / `BUGS_FOUND` 已有雏形；缺统一字段与第二方核对。
12. **`correct` 能（一部分）**：本仓已有引用、色板、渲染输入、账本、日期长度等结构性闸；但端口纪律、`worktrees --strict`、易变数字口径、不 `stash` 等仍只写在 markdown，没有检测。

**一句话收尾**：本仓不是一个「没有验证」的仓库——九道闸门、五道浏览器读数、反向用例、账本与旁证都是真的；但它是一个「**结果可复算、过程不可核**」的仓库。要建这套方法论，先承认这个分界，再按第 5 节的顺序补；不要从最贵的 `arena` / `swarm` 开始，也不要把「写了文档」当成「建成了」。
