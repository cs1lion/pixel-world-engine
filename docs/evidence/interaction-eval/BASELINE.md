## 评分器自身的校准（baseline 之前做的事）

第一次跑出来的读数不能直接当基线——评分器自己有三处口径错误，逐个修掉后
才重跑。这段留下来是因为「固定程序判别」的前提是程序本身可信：

1. `K2` 把 Vite 的 `/assets/index-xxx.js` 也算成素材请求 → 改成与
   `world-client/scripts/check-art-assets.mjs` 同口径，只算 `manifest.json` 与 `*.png`。

   改成读真实存档 `dengchao.pixel-world.save.v1` 的顶层 `schemaVersion`，
   并断言它必须是数字。
3. `K3` 最初要求「刚冻住就连续 8 帧逐字节相同」，但正式
   `world-client/scripts/check-ground-shadow.mjs` 的 `shotStable` 是等出现连续稳定帧，
   且前提更完整。做了 A/B：同样前提下 `art=1` 约 982 px 变化、`art=0` 约 816 px，
   **同量级**，证明零散变化不是动作表引入的。于是把判据改成真正该防的回归

## 一条被纠正的判断：L3-4 不是 spec 变更

实验 0 之后、动功能之前核对了 `world-client/scripts/check-interact.mjs` 的
L3-4：它查的是 `#unit-status` 里的输入控件数量与「干涉世界」提示语，而交互
动作按钮放在 `#villager-panel` 的独立容器，`#unit-status` 完全不变。
**那条断言不会红，也不需要改。**

先前把它判断成「有意的 spec 变更」是错的；若照那个判断去改一条本来绿的断言，
反而是在覆盖已工作的行为（EDD 文章里 VPN 那个例子的同型错误）。更正为：
L3-4 原样保留，「动作按钮不许漏进 unit-status」由本数据集的 M1 用
`forbiddenIn` 自己守。这一条更正本身也是 baseline 校准的一部分。

## 修正：走路没有步态，只是平移（2026-11-12）

用户指出「人物移动没有脚步和身体摆动动画，直接平移的」。查实后的根因与修法：

**根因不是播放、是素材。** 帧确实在切（冻结世界后逐动画帧推进，裁剪区像素变化约
1 万），身体起伏也在跑；但初版动作表的走路只有**两帧、正面朝向、腿几乎不动**，
只剩整体错位。正面两帧读不出抬脚，屏幕上就是平移。

**修法（三层）**

1. **走路独占一行四帧**（接触 / 下沉 / 经过 / 抬起），`carry` 并入 `walk`：
   拿着东西也在走，步态本就该照常摆动；素材里那两帧「推车」本来也与
   `carrying` 的三种物品对不上。
2. **走路帧单独生成再合成**：整表一次生成时模型会把走路行画成侧面、把参考图
   里的草帽少年画进来（实测 v0 跑偏）。改成用「该角色立绘 + 现有动作表」双锚点
   单独生成四帧步态条，再合成回第 2 行，其余行一像素不动。
3. **身体起伏改成跟帧号走**：抬脚那一帧抬高 1px，读成一步一顿；沿用时间驱动的
   起伏会和位图帧错位，看起来只是整块在抖。

**客观判据**（不是“看着还行”）：量四帧之间的「腿区变化 / 头区变化」。
整块错位会让两区一起变，那读成抖动而不是抬脚；走路该是腿在动、头基本不动。
七件实测：v0 2.69、v1 5.40、v2 2.28、v3 1.33、v4 1.50、v5 1.54、v6 1.56，
全部 ≥ 1.2，已写进清单的 `walkLegOverHead` 字段，并由
`test/action-frames.test.ts` 的最后一条守门（低于 1.2 或不足四帧就红）。

**证据**

- `walk-cycle-contact.png`：七人 × 四帧并排，能逐人看出换腿与抬脚。
- `walk-cycle-v3.gif`：四帧循环（83ms/帧），直接看动态。
- `walk-in-game.png`：游戏内实拍四帧（钉住位置、逐动画帧推进），
  裁剪区逐帧像素变化约 3.2 万，说明屏幕上真的在摆腿。

**已知取舍**：走路条的视角比其它行更侧一些（约 20°），从正面待机切到走路会有
一点转向感；换来的是步态能读出来。要彻底消除就得把待机也改成同角度重画，
成本另计，单独裁决。
