版本向量三轴已定死：「亮/灭 × 潮位 × 相位」（交接口径）。仓内可检索到的旧实现是 HD-2D P2 留下的两轴 (terrainVersion, structuresVersion)（docs/investigations/HD2D_P2_TILT_BAKE_NEGATIVE.md:40）， 不是本线要用的那三轴。按上表：lit 与 phase 直接是两轴；潮位 level 是连续量（0..1， lampPoolBands(level) 连续改半径与强度），进版本向量就意味着必须先离散成档，否则每帧潮位都变、 纹理每帧重烘，双缓冲 a/b 就失去意义 —— 这是动代码前要补的最后一条口径，本表不替你定档数。 呼吸 / 亮度 / sway 一律走 Image.alpha 与 setPosition，不进闭包、不烘进纹理； 双缓冲新烘完才换指针，不许 remove 掉还在用的纹理。

3. 差表【测】2026-11-09 实测：三块全部留活

3.1 口径

  • 装置：?bake=shade|pool|body|bodySorted 一次只开一块；另设 none（自校验）与 blank（空层对照）。bodySorted 与 body 同样烘 lampRows，但把 Image 用 scene.children.moveTo 插回原 Graphics 的 displayList 索引，恢复同 depth 渲染顺序， 用来分离「保序问题」与「α 叠色本质差」这两种成因。
  • 触发时机：冻世界 / 钉潮位 1 / 晴 / 氛围隐藏 / 三支动态关 → 200 帧沉降 → 显式置 window.__LIGHT_BAKE_NOW__ → 再推进 2 帧。不在第一次 update() 烘（那时 debug 设置未生效）。
  • 图：1010×700 视口下 canvas clip（960×640）；shotStable 连续 8 帧一致才截。
  • 基线：产品代码未改时抓 before-none.png，sha256 前 16 位 ba55dd0ad14d4532 —— 与建筑烘焙 tmp/building-bake/bisect 的基线同哈希，口径同源。
  • 比对：浏览器内解码 PNG，逐像素取 RGBA 四通道最大差；count = 非零差像素数，max = 最大色阶差。
  • 烘法：把该块当帧 Graphics 的 commandBuffer 用 generateTexture 烘成 1024×768 全图纹理 （设定集 64×48 格 × 16px），贴回同一 depth 的 Image，隐藏原 Graphics。与 buildings.ts:bakeStaticLayer 同一条 Canvas2D 合成路径。
  • 证据：world-client/tmp/light-bake/ 下的 before.json / after2.json / after3.json 与各配置 PNG， 脚本 world-client/tmp/light-bake-shots.mjs。端口 5211 + --strictPort，连接前过树身份闸。 body 在两次独立跑（after2 / after3）里 hash 同为 42772f29599dcd8e，读数可复现。

3.3 归因（差 ≠ 0 就留活，但成因要分开）

  • shade / pool：差沿整条灯街分布（bbox 横跨 960 px，分桶散在多个 100×100 区），量级 max 14 / 17，与建筑烘焙「未烘层」的 α<1 叠色差同类（back 4,096 px/max 1、 招牌 5,052 px/max 31，OPEN_ISSUES.md:1293–1297）——烘一张再叠回地面 = 两次合成。 本质差，留活。
  • body —— 两种成因已用 bodySorted 对照分离【测】：
  • body 的 max 114 是完全不同的颜色（暗青绿 → 暖橙灯笼色），来自同 depth 渲染顺序： add.image 默认插到 displayList 末尾，盖住了本该盖住它的东西。这是装置引入的。
  • bodySorted 把 Image 移回原 Graphics 的索引后，max 114 → 1，剩下 3,452 px 全是 ±1 量化差（样本 [131,108,81]→[130,108,81]）。上轮「114 是保序问题」的推断已被实测证实。
  • 剩下的 max 1 与建筑烘焙「未烘层」的 back（4,096 px / max 1）同量级、同成因： 烘一张再叠回地面 = 两次合成的舍入。这是本质差，不是包围盒或顺序能消掉的。
  • 仍非 0 ⇒ 按判据仍留活。 若将来要放宽到「容差 1 可接受」，那是改判据、要单独裁决， 本轮口径是「差非 0 就留活」，不改。
  • 作废的脏读数：第一次跑（未显式触发、烘在第一次 update()）读到 shade 34,284 px/max 32、 pool 52,716/max 18、body 5,996/max 177 —— 烘到的是错帧内容。已作废，一切以 after2 为准。

3.4 结论

三块差全非 0 → 按「差非 0 就留活」，三块全部留活，本轮不烘任何一块，7,102 条的 烘焙收益在本口径下拿不到。

上轮留的两个岔路，第二个已经走完并关闭：保序修复（bodySorted）把 body 的 max 从 114 压到 1，证明那 114 是装置问题；但 1 仍是两次合成的舍入，不会因改成紧贴内容的包围盒纹理而变 0 （blank 已证全图透明 quad 本身 0 伪影，包围盒能省的只有纹理尺寸，省不掉这一次额外合成）。 所以「改包围盒 + 重试 body」没有可期待的收益，本线到此可以收口。

结论只对本装置（全图纹理 + Canvas2D 烘一次 + 同 depth 顺序已保）成立；要翻案只有两条路， 都要单独裁决而不是调参：改判据（允许容差 ≥1）或换合成路径（不走 generateTexture 再贴回）。 本轮都没做。

4. 命令数差【算】

  • 灯亮帧：三块全烘，renderStats 减 7,102 条；Image +N / Graphics −N，Image 在 renderStats 记 0 —— 与建筑烘焙 OPEN_ISSUES.md:1285 同义：是「从统计里消失」，不是 GPU 少画 7,102 个 quad。
  • 灯灭帧（noon）：lampLight 只剩 16、lampPool 为 0，省不到 7,102。所以只能写成 「灯亮帧的存量」，不能写成「峰值下降 7,102」。
  • 预算余量：建筑烘焙后 check-ground-shadow 余量 6,590（28,076 / 天花板 34,666）、债务 0； check-render-budget 25,167 / 债务 0。这两个数与本表的 7,102 不同源、不相减。
  • 本轮实测装置不产生命令数下降（各配置一律 28,339，见 §3.2）。上面两条是「若最终实现 真把三块烘掉」的推算，不是本轮读数。
