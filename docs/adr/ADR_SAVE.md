# ADR_SAVE：存档这一层自己定的事

> 也就是说，这些引用指向的是一份从未被写下来的约定。
>
> 2026-10-27 从代码反推出本记录。凡是从代码里读得出来的一律给出证据（指名，不叫行号——
> 行号会漂，而仓库的引用审计只查「那一行有没有代码」，查不出「那一行是不是说的那个东西」）。
> 凡是从代码里读不出来的（当初为什么这么定、否掉了什么替代方案），**这里明说读不出来**，
> 不编。本记录因此是一份「现状说明」，不是「决策复述」——它证明这些规矩现在成立，
> 不证明它们当初被这样论证过。

## §1 存档只序列化世界自有事实

**规矩**：`Simulation.toSave()` 落进存档的只有世界自己的事实；上游的链接态与派生计数不入档。

**证据**：`toSave()` 的顶层形状是逐字段手写的，没有 `...this`——世界这个对象本身不被打散进存档。
（**元素级**的展开是有的，而且到处都是：`{ ...building }` / `{ ...prop }` / `{ ...task }` /
`{ ...record }`，`critters` 还额外把 `at` 拆开复制。那些是深拷贝，不是「把整个对象存进去」，
两件事别混。）
上游链接态（任务是从哪条事件流来的、当前同步到哪一刻）与派生计数（这一场起了多少楼、
攒了多少信仰）都不在落档的字段里。派生计数可以从落档的事实重算，所以它们不是「事实」，
是「算法的中间结果」——把中间结果存进去，等于让存档同时承认两份真相。

**读不出来的**：为什么选「只存事实、可重算」而不是「连派生计数一起存」。从代码看不出
当初是否比较过另一个方案。

## §1.2 读档必须在建世界之前，且网格按存档的落位重放

**规矩**：读档发生在建世界、起 Phaser **之前**；网格不存 `cells`，只按存档里的
`buildings` 顺序重放落位。

**证据**：`src/main.ts` 顶层先 `saveStore.read()` 再建场景；`rebuildGridFromPlacements()`
逐栋 `grid.place(...)`，任一枚落位失败即 `WorldSetupError`。分区与铺子的不变量在读档后
仍要过一遍（`buildWorldFromSave` → `assertWorldInvariants`）。

**这条规矩真正防的事**：网格是算出来的，不是存出来的。`cells` 一旦入档，存档就和
「分区表、铺子表、地形表」这三份配置绑死——改任一配置，老档读出来就是一张错的地图。
只存「谁在哪」，地图永远由当前的配置重算。

**代价（代码里看得见）**：老档的 `palette` 可能属于旧色表，所以读档后按 `prefabId`
重解颜色，找不到 prefab 才回退存档里的存量值并告警。这是「颜色是显示事实、以当前表为准」
与「存档是唯一真相」之间的一次让步，见 `setup.ts` 里读档重建那一段的注释。

## §1.3 校验分两层，两层防的不是同一件事

**规矩**：

1. **路径集合包含校验**——存档里出现的每条叶子路径都必须落在允许集合内，越界即拒并指名。
   它**只防「新增字段」**。
2. **字段级校验**（`validateSaveFields`）——逐字段查类型、范围、存在性。
   它防「删字段」「换错类型」「值越界」。

**为什么必须是两层**：删字段会让路径集合**合法地缩小**——第 1 层对此完全无感，
一个少了十个字段的存档能顺利通过集合包含校验。所以「少字段」这一整类只能由第 2 层兜。

**纪律**：一律**拒绝**，不静默补默认值。缺一个字段就是坏档，不拿 `??` 猜。

**旧版自证**：每个曾经的当前版本各有一条自证校验（`assertSaveV1` / `assertSaveV2` /
`assertSaveV3`）。理由是硬的：一个版本一旦不再是当前版本，迁移链就会**先改写它再校验**，
那道「先自证」的关口就空了——一个被改过的旧档会被安静地迁成新档。所以旧档在被迁移之前
必须先证明自己是自己。

**一个曾经的缺口（2026-10-27 实测，同日已补）**：`checkPoint()` 原来声称校验「整数、落在世界内」，
两半都不成立——三个调用点故意不传 `{ integer: true }`（那些点是 `Vec2`，带小数是对的），
而「落在世界内」这一层**根本没有**：`validateSaveFields` 跑在原始 JSON 上，那时还没有网格，
而世界多大是 `GridSpec` 参数，存档这一层不知道。实测把手改存档里的
`villagers[0].pos` 改成 `{x: 99999, y: -98765}`：校验放行、`fromSave` 原样恢复、
之后每一步 `at()` 都返回 `undefined`——不抛、不记日志，她只是从此看不见也够不着。
命令那条路是有人拦的（世界会回「那里在世界外面。」），所以这个洞只有手改存档才够得着。

**补法（同日）**：新函数 `findOutOfWorldCoordinates(save, bounds)`，收 `{width, height}`
两个数，返回一行一条的界外坐标指控（指名到 JSON 路径）。由 `parseSaveText(text, bounds?)`
在读档与导入两条路上调用；命中即按坏档处理——备份原档、用新世界启动、把越界的坐标说清楚。
`bounds` 由建世界的那一方递进来（`main.ts` 传 `pack.grid.width/height`），
不递就只做形状校验：那是**知道有洞而不查**，不是「查过没问题」。

**为什么是这六类，以及为什么不是防「世界跑偏」**：世界自己的寻路只会产出界内格子
（`grid.path()` 的 `passable()` 要求 `at()` 有值，越界即 undefined；兜底的
`nearestWalkable()` 只扫 `0..width`/`0..height`）。实测佐证：大世界 96×72 跑
240000 拍（64 分钟世界时间）、八轮派活覆盖四类活，`pos` 与 `path`/`pendingRoute`
的格子全在界内。所以这道闸防的是**存档坏了**，不是世界跑偏。

**建筑也并进来了，但别以为落位合法也一并查了（2026-10-27 当日补掉）**：`rebuildGridFromPlacements()`
放不下就抛 `WorldSetupError`，而那道抛错在 `main.ts` 顶层没有人接——白屏，只留一条
console 错误，玩家连「存档有问题」都看不见。把建筑的三类坐标并进 `findOutOfWorldCoordinates`，
同样的存档从「白屏」变成「备份 + 新世界 + 说明」。

但**坐标在界内不等于摆得下**：两栋楼重叠、门落在自家占地里、门到不了镇心，这三类的
坐标全都规规矩矩在界内，形状校验一路放行。实测三种各造一份坏档：`parseSaveText`
连 `bounds` 一起查也全部放行，而 `buildWorldFromSave()` 三种全都抛
`WorldSetupError`——仍然白屏。

**补法（同日，与界外坐标那道同一个形状）**：`SaveStoreOptions.tryBuildWorld` 收一个
`(save) => string | null`，由 `main.ts` 递进来。**没有在存档层另写一套落位判据**——
那套规矩住在 `WorldGrid.place()`，还要蓝图表、`GridSpec`、祭坛三个入参，存档层一个都没有；
照抄一份就是第二份真相，`place()` 将来多一条不放行的路子，抄的那套不知道。递进来的
就是开工要用的那个建造函数（`main.ts` 的 `buildWorldFor`），所以检查的与建造的
不可能是两套。命中即按坏档处理：备份原档、用新世界启动、指名是哪栋楼；
`importText()` 同一条链，拒绝且不写槽。

**它防的仍是存档坏了，不是世界跑偏**：世界自己落位全走 `checkPlacement`，落地即合法。
三种坏档都只有手改存档（或导入别人的档）才够得着。

## §2.1 `settled[]` 是去重的唯一真相

**规矩**：一条活结算过没有，只问 `settledLog`（`isSettled()` 线性扫）。

**证据**：`settledLog` 是私有字段，注释写明「save-only，不入快照」——它是账本，
不是给人看的状态。`recordDelivery()` 是交付的唯一漏斗，三处交付都经过它。

## §2.2 分账：上游与本地分开，时间戳不顶替

**规矩**：`SettledRecord` 分 `source: 'ledger' | 'mock'` 与 `workerId`；日报按人分账。
`completedAt` 只认上游事件时间（`task.settled` 带来的 `completedAt`），**缺失记 null，
禁止本地时间顶替**；`'mock'` 才用本地 wall clock，并记在 `completedAtClock` 里。

**这条规矩真正防的事**：把本地时间填进上游字段，会让一条「上游说什么时候完成」的记录
从此无法与上游对账——而它是唯一能证明「这件事真的发生在上游」的字段。
两个字符串 `'ledger'` / `'mock'` 是 v1–v3 的字面量、冻结着；语义已换成
「事件流派来的」与「本地造的」。

**顺带**：已结算记录超过 `SETTLED_WARN_THRESHOLD`（5000）告警一次，每会话一次。

## §3 迁移是逐级链，任一步抛错都拒绝加载

**规矩**：`MIGRATIONS` 是一张 `版本号 → 迁移函数` 的表，从存档自报的版本一级一级迁到当前。
任一步抛错，整次加载失败——不跳过、不部分应用。

**现在的链**（`CURRENT_SCHEMA_VERSION` 为 4）：

- v1 → v2：世界变活。见 `ADR_WORLD_ALIVE §8`（那份记录同样迟到——见其开头的说明）。
  补的是 `SAVE_V2_ADDED_PATHS` 那 15 条路径，横跨 buildings / critters / oracle / props。
- v2 → v3：加潮汐覆盖与灯油余量。
- v3 → v4：四样——`villagers[].nameState`（名牌两态）、`villagers[].carries`（随身凭证）、
  `props[].grime` 与 `props[].reveal`（摆件的尘与显隐），并把 `meta.schemaFingerprint`
  重算成 v4 的。

**为什么逐级而不是一步跳到当前**：每一级只需要知道自己前后各一个版本。写成
「v1 直接改写成 v4」的话，链上每加一级，那个函数就要多认一种旧形状。

## §4 写档时机：只在 `update()` 返回后

**规矩**：自动存档只在一帧的世界推进**返回之后**调用（命令已结算）。

**证据**：`SandboxScene` 的帧末顺序是 `sim.update(...)` → `snapshot()` → 渲染 → 相机 →
小地图 → `maybeAutoSave()`。交付 / 施工 / 神恩 / 30 秒节流这几条写档路径同样守在 `update()` 之后。

**这条规矩真正防的事**：在 `update()` 中间写档，会把「进行到一半」的状态落进存档。
读档的人看到的是一个世界从未抵达过的瞬间——角色在半路上、任务在结算中途。
更糟的是那一帧未必可复现，于是同一份存档两次读出的行为不同。

**`save-store` 那一半（§3/§4，标着 final）**：

- **单槽**：`SAVE_STORAGE_KEY` 从 v1 起就没变过。升 schema 不改存储键，老档才读得到、
  才谈得上迁移。
- **坏档先备份再提示**：`backupCorrupt()` 原样备份、带时间戳、只留最近 3 份；
  备份失败不影响主存档。提示语是「存档损坏，已备份原档，用新世界启动。」
- **配额降级**：主槽写失败（配额/安全异常）→ 关自动存档、提示一次、不抛。
  配额紧张时**先删最旧备份**再重试主存档——备份不得拖垮主存档。
- **导入高版本只读**：版本高于当前的导入，拒绝、不迁移、不降级、不写槽、不备份
  （原文件在用户手里，动它没有意义）。
- **读档永不抛**：任何异常都降级成可读的结果对象，理由分 `empty` / `corrupt` /
  `version` / `storage`。

## §5 `meta` 是诊断，永不喂逻辑

**规矩**：`meta.savedAtWallClock` 与 `meta.savedReconciled` 仅诊断，不进任何逻辑判断。

**证据**：`meta.schemaFingerprint` 是唯一被逻辑读取的 `meta` 字段（存在且不符 → 按坏档处理），
另两个只在写档时记录。

**这条规矩真正防的事**：`savedAtWallClock` 是墙钟。世界自己不读墙钟——潮汐、作息、
固定步长全都吃世界自己的 `now`，确定性回放靠的就是这一条。一旦有逻辑开始看墙钟，
「同一天重开是同一片海」就没了。

**同一个洞见的另一处**：`world.worldChangeVersion` 目前**只存不用**——`GLOSSARY.md`
里记着它是预留给事件日志的存档字段，`src/` 与 `test/` 下没有读者。
