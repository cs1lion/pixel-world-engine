# ADR：记忆按世界日序号命名，不按日历日期

- 状态：已接受
- 日期：2026-10-26
- 关联票据：#7
- 上游：`docs/SPEC.md` §4.7、`docs/SPEC_V2.md` §3（第 13–16 条）

## 背景

SPEC §4.7 给的目录示例是：

    memory/
    ├── entries/2026-10-25.md        每日快照：潮位、天气、大事
    └── index.yaml                   索引

而 #7 的验收条件里有一条：「每日快照能从事件日志重新生成，与落档内容一致」。

这两条放在一起有个矛盾。事件的 `at` 是**世界时间**——固定步长推进的毫秒数，
回放时按它重放，跟服务器什么时候写进这条日志无关（`events/log.py` 开头第 3 条）。
而「2026-10-25」是一个日历日期，它只能来自墙钟。

## 决策

`entries/` 下的文件名用**世界日序号**：`day-0007.md`。一天 = 24 个世界小时
（`snapshot.py` 的 `DAY_MS`），第几天 = `floor(at / DAY_MS)`。frontmatter 里带
`from_ms` / `to_ms` 的世界时间窗口，人照样能锚定。

    memory/entries/day-0007.md

## 理由

**墙钟会让「能重新生成」变成假的。** 同一个 `day` 两次 derive 必须字节相同，
这是验收条件。文件名里带日历日期的话，快照内容就含一个每次跑都不同的值——
要么两次生成不一致（验收直接红），要么把日期从内容里剔掉、只留在文件名里
（那文件名就不是派生的一部分，改了时钟旧文件就孤儿了）。两条路都比序号差。

**世界时间才是这个仓库里唯一被允许的时钟。** `EventLog` 的 docstring 第 3 条、
`rules/schema.py` 的「校验是纯函数」、`purity.test.ts` 的「潮汐逻辑不读墙钟」
说的是同一件事。记忆是世界的记忆，它该跟着世界的那根钟走。

**人不吃亏。** frontmatter 的 `[from_ms, to_ms)` 是精确的世界时间窗口，
比一个日历日期更可查；真要给人看的日历日期，由读的人自己换算，那是一次展示，
不是一条事实。

## 后果

- 好：快照是日志的纯函数，`derive(log, day) == derive(log, day)` 有测试钉住；
  重跑一次不该让 `git status` 多一行改动，也有测试钉住。
- 好：换机器、换时区、改系统时钟，都不影响记忆文件长什么样。
- 代价：`day-0007` 读起来不像日期。缓解是 frontmatter 的时间窗口，以及
  `memory/README.md` 里写明了怎么换算。
- 将来若要日历日期：那是一次**展示层**的决定，该在生成给人看的页面时做，
  不该进文件名——那时要走的理由是「人要的是日期」，而本条 ADR 挡的正是
  「把展示用的东西塞进事实层」。

## 备选

| 方案 | 为什么没选 |
| --- | --- |
| `entries/2026-10-25.md`，日期由调用方传入 | 调用方得自己有时钟；同一个 `day` 换个调用方就换个文件，「重新生成」没有唯一答案 |
| 两个目录：`entries/` 按序号、`daily/` 按日期 | 两份快照，两份真相。要么分叉，要么其中一个永远是装饰 |
| 文件名不带日期，只靠 frontmatter 锚定 | 人在文件管理器里点不开任何一个。记忆的本意是「读文件就知道上周发生了什么」 |
