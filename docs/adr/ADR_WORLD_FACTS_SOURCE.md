# ADR：世界上有哪些楼——客户端报现状，日志投影只做兜底

- 状态：已接受
- 日期：2026-10-27
- 关联票据：#16
- 上游：`docs/SPEC.md` §4.2（L1 的三条铁律之一：任何命令必须过 Schema）、§4.3（`building.remove`）

## 背景

#16 的验收条件里有一条「越界请求被拒率必须 100%」。首轮实测 11/12，漏的是
「拆掉第 999 号楼」：模型答了 `building.remove`，instanceId 编了一个世界上
没有的值，而 `rules/schema.py` 的 `_building_remove` 只查「是不是非空字符串」
就放行了。

归因不在模型。模型确实说了句越界的话，但**服务端那时答不出「世界上有哪些楼」**——
`/api/world/intent` 手里的世界摘要只有客户端发来的 `worldSize`。坐标越界在
`_point` 里就拦了，实例存在与否没有理由放到世界那一层再答一遍。

于是要给白名单一份建筑清单。手上有一条现成的：世界把建了什么回写进了事件日志
（`building.built` / `building.removed`），按 id 升序重放就是一个集合。
`events/projection.py` 就是这么写的，也真的把「拆掉第 999 号楼」拦住了。

但它是**错的**，而且错得很安静。

## 决策

建筑清单有两条来源，优先序固定：

1. **客户端报的现状**（请求体里的 `context.built.town` / `.wild`）——**主源**。
2. **事件日志投影**（`events/projection.py` 重放 `world.changed`）——**兜底**，
   只在客户端没给出能用的建筑清单时用。

地图尺寸仍然只听客户端的（`worldSize`）：地图是设定集的内容，服务端没有它。

「客户端报了但为空」与「客户端没报」是两件事：前者是世界此刻的事实，
用空集；后者才回去翻日志。**两组 `built`（`town` / `wild`）必须都是数组
才算「报了」**——少一组就是没报完。只报 `town` 的客户端会让所有野外的楼
凭空消失，于是每一句「拆掉那栋渡口」都被拒，而日志里明明记着它建成过；
宁可回去翻日志，日志不全，但不会凭空归零。

日志读不动时，世界摘要降级成「不知道」，存在性检查整项跳过，**不给 500**。
**降级只覆盖建筑那一半**：尺寸是客户端直接发来的，与日志好不好没有关系，
必须活着出去——坐标越界检查靠的只有 `width` / `height`。

## 理由

**日志记的是变更，不是快照。** 开局就有的楼（设定集落的）从来没有
`building.built` 事件——客户端只对**运行时新建**的楼发回写。所以一个会话里
日志出现的第一条建筑记录往往是一次拆除：那一刻投影的口袋是空的，
`recorded` 刚被翻成 `True`，`ids` 还是 `()`。于是 `to_world()` 说
「一栋楼也没有」，之后**每一句**「拆掉它」都被拒成 `unknown-instance`，
还附一句「现在一栋楼也没有」。世界明明还在好好地建楼拆楼。

这不是理论风险，是拿日志当全集时**每一个会话的第一次拆除之后**都会发生的事。

**世界的现状只有世界自己知道。** 客户端从模拟快照里直接搬，那是它能做而且
已经在做的事（`worldSize` 就是这么来的）。让它多报一份建筑清单，比让服务端
从变更记录里反推快照便宜，也更准。客户端报事实、服务端定规矩，这条分工
本来就在那儿，只是建筑那一半一直没走这条路。

**模型不写请求体。** 所以客户端这一侧不是攻击面——把 `context.built` 当权威，
不会让模型多拿到一分自由。要防的是模型编 id，而那正是 `_building_remove`
要拦的。

**读日志失败不该让端点长出第四种结局。** 端点的失败面写死了三种：
503（没配 Key）、422（请求形状不对）、200 + unknown（没听懂或越界）。
日志坏着的当口，仍然该把「下雨吧」翻成天气命令，只是这一句不再查存在性。
多一个 500 就是多一种客户端没准备过的失败，少的却是白名单里本来照常生效的
那几项检查。这与「证不明就不判」是同一条纪律：**没有记录 ≠ 世界上一栋楼也没有**。

**同一份摘要顺带修好了另一处。** `MAX_BUILDINGS` 那道上限此前从来没有生效过——
`buildingCount` 压根没被传进白名单。现在传了。

## 后果

- 好：拆一栋开局楼不再被拒。`test_projection.py` 里
  `test_客户端报了建筑就以它为准_哪怕日志里一栋也没有` 钉的就是这个场景。
- 好：白名单第一次真的能回答「世界上有哪些楼」，「拆掉第 999 号楼」这类
  越界请求有了第二道闸。
- 好：端点没有新增失败面。日志读不动 → 降级 → 200，有测试钉住。
- 代价：客户端必须真的报 `context.built`。老客户端不发，服务端就退回日志投影，
  于是回到上面那个「第一次拆除之后全被拒」的老问题。缓解是这条 ADR 与
  `intent-context.ts` 的契约——但那终究是一份**约定**，不是编译期保证。
- 代价：每次意图请求都要分页读全量日志（不读「最近 1000 条」——第 1001 条
  之前建的那栋楼会从投影里消失，于是「拆掉它」被误判）。世界的事件量到几千条
  之前不算什么；真到了那一天该加的是缓存，不是把上限当默认值。
- 代价：实验脚本比线上更严。它传 `context=None`，走的是日志投影那条更窄的路。
  这是故意的：提示词是第一道闸，白名单是第二道，只验第二道才说明它真的拦得住。

## 备选

| 方案 | 为什么没选 |
| --- | --- |
| 只用日志投影 | 见上：开局楼不在日志里，每个会话第一次拆除之后每一句 demolish 都被拒 |
| 日志为主，客户端只补差额 | 两份真相，还得先回答「谁覆盖谁」。而客户端那份本来就更新、更全 |
| 让世界（服务端）持有一份建筑状态表 | 那才是快照的正确住处，但世界的权威状态在客户端的 `Simulation` 里；服务端再存一份就得处理两边分叉，代价远大于收益 |
| 客户端报了就用，报错也当「一栋也没有」 | 一个客户端的形状 bug 会变成「世界是空的」，于是每句「拆掉它」都被拒——正是本条 ADR 要避免的那种错 |
| 只报了一组也当完整现状 | 见上：野外的楼会凭空消失。少一组整体退回日志 |
| 日志读失败就 500 | 端点只有三种结局，这是第四种；而且为一句辅助信息牺牲整条解析路径 |
| 日志读失败时把尺寸也一起丢掉 | 坐标越界检查靠的只有尺寸。「在 5000,5000 建个工坊」会因此堂而皇之地过闸 |
