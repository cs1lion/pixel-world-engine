# R1a「分辨率参数化」评估：为什么这一轮停手

- 日期：2026-11-02
- 分支：`refactor/tile-metrics`（从 `main` 起，未 push）
- 依据：外部 HD-2D 改造评估的第六节「R1 的可执行改造清单」（临时输出目录，未入库）
- 结论：**按 T5 的停手条件停止**，本分支只提交这份评估，不改渲染代码。

## 一、停在哪一步

计划把 R1a 定义为「只参数化、画面零变化」，但它同时包含两批工作：

1. **批次 1（常量与数据）**：`TILE_PX` 变成 `SettingPack.tilePx`，场景解析一次，传到渲染层。
2. **批次 2（渲染层去硬编码）**：把 5 个主渲染文件里所有格内偏移按 `s = TILE/16` 重排。

批次 2 不是「改一个常量」，而是**重写整套像素坐标语法**。按仓库现状统计：

| 文件 | `fillRect(` 次数 |
| --- | ---: |
| `world-client/src/render/buildings.ts` | 155 |
| `world-client/src/render/decor.ts` | 88 |
| `world-client/src/render/villager.ts` | 83 |
| `world-client/src/render/tilemap.ts` | 79 |
| `world-client/src/render/setting-scenery.ts` | 51 |
| 其余 13 个 render 文件 | 88 |
| **合计** | **544** |

- 全仓 **21 个源文件**直接 import `TILE_PX`；把它换成参数意味着这 21 处的调用签名一起改。
- `check-creation.mjs` 里还有两处 `cell.x * 16` / `cell.y * 16` 的硬编码（脚本侧，不在 render 层）。
- 地形与雾是**整图烘焙**（`bake.ts` 单张纹理、`fog-view.ts` 整图），T48 会超过 4096 上限，批次 3 的切块不是可选项。

这与 T5 里写明的停手条件一致：**参数化会牵连渲染热路径，需要大改。**

## 二、为什么不能用「容器整体缩放」抄近路

看起来最省事的办法是：内部仍按 16px 坐标画，给每个容器 `setScale(s)`。它在本仓不成立，原因是坐标系有三层：

1. **世界坐标**：相机、Y-Sort、`depth = ALTITUDE + baseY`、小地图、点击热区都用 `格 × TILE_PX`。
2. **容器内部坐标**：门/窗/檐/烟囱的偏移是 `building.door.x * TILE_PX - px` 这类「世界减容器原点」的差值。
3. **烘焙纹理坐标**：地形与雾先画进一张离屏纹理，再以 `(0,0)` 贴回世界。

只缩放容器，会让第 1 层（世界锚点）与第 2 层（内部偏移）各自乘一次不同的比例；而烘焙纹理是**位图**，缩放它只会放大 16px 的像素，不会增加细节——那正是 R1a 不该做的事（R1a 要「改得看不出来」，R1b 才「真的变高清」）。

要同时改对，得把第 2 层每个字面量按 `s` 重排、把第 1 层所有 `TILE_PX` 换成运行时参数、把第 3 层改成按块烘焙。这就是批次 2 + 3 的全量工作，不是一次「抽常量」。

## 三、需要的改动量（给下一位执行者）

按计划原清单，最小可交付顺序是：

| 批次 | 内容 | 预估 | 风险 |
| --- | --- | --- | --- |
| 0 | 冻结基线：固定机位/时刻截图、烘焙耗时、帧率、指令数 | 0.5 天 | 当前本地浏览器回归受**时段**影响（见第四节），必须先解决 |
| 1 | `SettingPack.tilePx` + `tilePxOf(pack)` + 校验 `{16,32,48}` + 场景解析 | 0.5–1 天 | 低；16 下应逐像素不变 |
| 2 | 544 处 `fillRect` 的偏移按 `s` 重排（5 个主文件占 456 处） | **5–8 天** | 高；每一处都可能引入 1px 漂移，必须靠截图 diff 兜底 |
| 3 | 烘焙切块（地形/雾）、潮汐/天气尺寸、雾 puff 尺寸 | 2–3 天 | 中高；4096 纹理上限与显存 |
| 4 | 相机默认档、`labels.ts` 锚点、`check-creation`/`smoke` 的 16 硬编码、截图基线重拍 | 1–2 天 | 中；交互点选与 overlay 对齐断言会红 |

**结论**：R1a 不是「半小时抽常量」，而是 **8–13 个工作日**的渲染重排，且必须在稳定截图基线上做。本轮时间与基线条件都不满足，硬做只会得到「16 下看起来一样、32 下到处裂缝」的半成品。

## 四、为什么今晚的截图基线不可信

同一份 `main`（`408da3c`）的浏览器回归：

- CI（UTC 15:xx）通过：`神谕闭环：124 项通过`。
- 本地（Asia/Shanghai 23:xx）连续两次在同一项失败：`超时：她停下手里的事行礼`，最后状态是 `routine: 回祭坛`。
- 用 `main` 的独立 worktree 复跑，同样失败——不是本轮 T2/T3 的回归，而是**时段相关**的既有波动：夜里她在回祭坛的路上，命令到达后行礼的时机与白天不同。

截图基线若在这种状态下拍，R1a 的「逐像素 diff=0」会拿一组本身就不稳定的对照。必须先给浏览器验收固定 `?time=noon&speed=1`（或等价的可控时钟），再谈像素基线。

## 五、与外部结论的关系

并行线已实测：HD-2D 只在 **48px 格径 + 门重画到约 61×86** 时成立；32px 会让人比门大两圈、头穿屋檐；一屏可见格数会从 150 降到 67。

这不改变本评估，只改变 R1b 的目标值：R1a 应先把 `tilePx` 做成可配且默认 16，R1b 再决定默认翻到 32 还是 48。**48 需要的切块（批次 3）与门重画（R2）都不在 R1a 里。**

## 六、建议的下一步

1. 先修浏览器验收的时段依赖（固定时刻），让截图基线可重复；
2. 做批次 1（只抽常量与数据，16 下逐像素不变），单独一笔提交；
3. 批次 2 按文件拆成 5 笔（buildings / decor / villager / tilemap / setting-scenery），每笔都跑 16 下截图 diff；
4. 批次 3–4 再动烘焙、相机与脚本硬编码。

在那之前，不建议把 `tilePx` 接进渲染函数却不缩放内部偏移——那会让「可配置」变成一句只对 16 成立的假话。
