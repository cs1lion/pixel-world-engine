## 已定的口径

v1.0 与仓库代码撞车的地方，定过一条：**一天 = 24 个世界小时，采用仓库的 `DAY_MS`**（2026-10-27）。v1.0 的 `day_length_seconds = 900` 因此按 `86400` 秒读，900 / 3600 降级为「现实里看完一天要多久」的节奏目标，交给前端时间倍率（`timeScale` 96 / 24；现状默认 6、`?speed=` 上限 60）。两组 README 的第 8 条记录了完整理由。

这条不是新决定，是沿用已有的：`docs/adr/ADR_MEMORY.md` 早已把「一天 = 24 个世界小时」定死（`GLOSSARY.md` 的「世界日序号」同义），前端 `world/lampoil.ts` 的 `LAMP_DAY_MS` 也是 24 小时——同一个长度在仓库里写了好多遍，本身就是把 24 小时当既定事实。所以 v1.0 的 900 秒只可能读成节奏，不可能是另一套「天」。

**这个数写了几遍，不在这儿手写。** 这里原来写的是「三处各写一遍」，并列了 `ADR_MEMORY.md`、`GLOSSARY.md`、`lampoil.ts` 三个名字——那个数是假的，那份名单也是漏的：它漏掉了上一行刚刚让读者「采用」的 `DAY_MS` 本身。2026-10-28 复核，**把这个长度定义下来的地方是五处**——注意是「定义处」，不是「出现处」：照着 `86400000` 全仓 grep 还会命中样例载荷、测试数据和几处注释，那些都不定义一天有多长。

| 位置 | 写法 |
| --- | --- |
| `server/memory/snapshot.py` | `DAY_MS = 24 * 60 * 60 * 1000` |
| `world-client/src/world/memory/config.ts` | `DAY_MS = 24 * 60 * 60 * 1000` |
| `world-client/src/world/lampoil.ts` | `LAMP_DAY_MS = 24 * 60 * 60 * 1000` |
| `docs/adr/ADR_MEMORY.md` | 文字：「一天 = 24 个世界小时」 |
| `GLOSSARY.md` | 文字：「一天是 24 个世界小时」 |

前三处是代码常量，由 `world-client/test/memory-day.test.ts` 钉住一致（服务端那份是从源码读出来的，不是再抄一个数）；后两处是散文，由 `world-client/test/day-length-prose.test.ts` 钉着——2026-10-28 补的。补之前这里写的是「散文那两处没有闸，所以这一条本身也会漂」；那句话在新闸立起来的那一刻就成了假话，所以改对。

注意这补的是**唯一还能漂的那一个方向**：代码那三处改 `DAY_MS` 会先被 `memory-day.test.ts` 拦住，而散文可以单独被改错（手滑、复制粘贴、或者从外部设计资料里抄个 `day_length_seconds = 900` 进来）而代码一动不动。新闸量的正是这个：散文里那个小时数与 `DAY_MS` 换算出来的不相等就红，句子没了也红。

**但「这一条本身也会漂」这句仍然成立**，只是换了地方漂：`day-length-prose.test.ts` 只认「一天 N 个世界小时」这一种句式。散文哪天换成别的说法，它会红——那正是要人回来重新指路的意思，别把新句式悄悄加进去而不看它。所以复核还是老规矩：重新数一遍，别信这张表。

**这张表不写行号。** 2026-10-28 我在这上一天栽了两次：`docs/SPEC.md` 里写「第 42 行的用户故事 11」，而那一笔自己往文件头加了 13 行，行号当场作废；同一天另一处引了「说着反话的那几行」。所以这里只留**能 grep 的记号**（常量名或原句），不留给任何一次编辑能推翻的数。要找就 grep `DAY_MS` / `LAMP_DAY_MS` / 「一天 = 24 个世界小时」，别看表里的位置。

**「五处」也不是个准数**：它是一个「定义处」的计数，换一天 grep 就可能多一处少一处。真想知道还有哪儿写了这个长度，就现 grep `86400000`，把命中逐条分成「定义」与「使用」两类再数。
