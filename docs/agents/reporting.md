# 交付报告纪律

适用对象：任何人（人或代理）在会话里、提交信息里、PR 描述里**汇报"做完了什么"**的文本。
不适用于代码注释、ADR、规格——那些有自己的闸门。

为什么写在这里：`docs/agents/` 收的是代理在仓库里的工作规则，这份规则管的是"汇报"这一环；
它必须和 `domain.md`、`issue-tracker.md` 一样在动手前就被读到，而不是等事故后现场定。
CLAUDE.md 里有一行指过来。

## 事故形状（为什么要写成规则）

有一条线报了"16 张 48 图已落地、三跑逐字节相同"，还附了带精确世界时刻的表格；
核查时脚本、目录、图片**全部不存在**，半小时后才补做。当时的处置是现场定规则
（每条事实带命令回显、落地贴 `Get-ChildItem` 与 sha256、通过贴退出码），
靠主控线盯着执行——换人换会话就退回去了。规则只活在会话里，等于没有规则。

## 触发条件（没有结构化块 = 未受检）

凡在会话、提交信息或 PR 描述里声称「产物已落地」「闸门已通过」「N 张不变 / 零差异」，
就必须把同一份证据落成 `docs/evidence/<slug>/README.md`，并带下面的机器可读块。
**只在会话里说、没有落盘报告的，`audit-reports` 一个字都查不到——未受检不等于通过。**
派活与验收的一方在采信这类结论前，先要 `docs/evidence/<slug>/README.md` 的路径；
拿不到路径的结论按「未交付」处理，不要用聊天记录当证据。
lint 只能扫仓库里的 `docs/**/*.md`，扫不到聊天窗口和提交信息，所以这条边界只能靠人守。

## 机器可读块

每份"交付报告"（`docs/**/*.md` 里以 `<!-- delivery` 开头的注释块）必须带一个 JSON 块，
人读正文、机器读块。正文可以叙事，块只放可核对的字段：

```md
<!-- delivery
{
  "artifacts": [
    { "path": "docs/evidence/stair-flight/before-street.png", "bytes": 37319,
      "sha256": "afee1acaa91b87009ab8bd5db5ea41476a948231d65dd1035300adc109359ed7" }
  ],
  "checks": [ { "name": "npm test", "exit": 0 }, { "name": "npm run check", "exit": 0 } ],
  "diff": { "method": "byte-exact", "threshold": 0, "size": "961x641", "shots": 2,
            "scope": "整幅 canvas；街面与渡口两个机位" },
  "status": { "state": "local-commit", "sha": "b351244d86d5fc3fe043211255e51a2e30627cef",
              "branch": "feat/stair-flight", "pushed": false, "pr": false },
  "reportedAt": "2026-11-07T00:20:00+08:00",
  "inferences": [ { "claim": "细条来自残雨", "basis": "形状是 2–4×10–14px 竖直条、数量随 intensity 回落单调减少" } ]
}
-->
```

没有块或以 `<!-- delivery` 开头却不是合法 JSON 的文件，`audit-reports` 直接报错。

## 七条规则

每条都写成"报告里必须出现什么"，并标明能不能自动查。

### R1 说"已落地"→ 清单 + 字节数 + sha256

- **必须写**：每个产物一行 `path`、`bytes`、`sha256`（64 位小写十六进制）。
  没有哈希的文件必须写 `noHashReason`（例如"生成物不可复现"、"二进制由外部工具直接写盘"）。
- **自动**：`audit-reports` 复核路径存在、`bytes` 与实际字节数一致、
  `sha256` 与实际内容一致（等价于 `Get-FileHash -Algorithm SHA256`）。
- **人工**：哈希是否对应**这一次**的产物——同名文件被后续运行覆盖时，lint 只看得到当前这份。

### R2 说"通过"→ 退出码或原始输出行

- **必须写**：`checks` 里每项一条 `name` + `exit`（整数）；正文至少贴一行可复核的原始输出
  （计数、阈值、`RESULT=` 之类），不能只写"通过"。
- **自动**：`exit` 是整数、`checks` 非空。
- **人工**：这条命令是不是真的在这次交付里跑过、输出是不是那次运行的——
  历史命令不会被 lint 重放，重放也不等于同一次运行。

### R3 说"N 张不变 / 零差异"→ 写清比对口径

- **必须写**：`diff` 里 `method`（`byte-exact` / `pixel-threshold` / `structure-block`）、
  `threshold`（数值，逐字节就是 0）、`size`（如 `961x641`）、`shots`（张数）、`scope`（范围：整屏还是裁剪、哪些机位）。
- **自动**：字段齐全；`size` 形如 `宽x高`；`shots ≥ 1`；`method` 含 `byte` 时 `threshold` 必须是 0。
- **人工**：两组图的分辨率是否真的一致、`scope` 是否恰好漏掉了变化区。
  "169 张基线逐字节不变"栽的就是尺寸先变了而口径没写——尺寸只能靠写，不能靠 lint 猜。

### R4 实测与推断分开，推断要写依据

- **必须写**：`inferences` 数组，每条 `claim` + `basis`。正文里的推断句以 `[推断]` 开头。
  `basis` 说明凭什么：形状、幅度、单调性、排除法，不能写"应该""大概"。
- **自动**：每条 `basis` 非空且不少于 8 个字符。
- **人工**：哪句话属于推断、依据是否成立——这是语义判断，lint 不做自然语言判断。

### R5 写清提交/推送状态

- **必须写**：`status.state` ∈ `uncommitted` / `local-commit` / `pushed`；后两者带 `sha`（40 位）
  与 `branch`；`pushed`、`pr` 是布尔。`status` 描述**被报告的工作**，不描述报告文件本身。
- **自动**：枚举、sha 格式；**非浅克隆**时用 `git cat-file -e` 验证该 sha 在本仓存在
  （浅克隆会误判，所以跳过并打印跳过原因）。
- **人工**：远端是否真有该分支（要网络与凭据）、PR 是否存在（要 `gh` 或网络）。
  lint 不联网，避免把"没网"报成"没推"。

### R6 产物时间不得晚于报告时间

- **必须写**：`reportedAt`，ISO 8601 含时区。字段仍在，但它**不作为判据**：这里不再提供
  mtime 或 `reportedAt` 兜底——那是给作者留的「填数字关掉」口子，规则明确不收。
- **自动（主判据，git）**：报告侧取报告文件的 git 提交时间，产物侧取产物自己的 git 提交时间。
  两侧都要「已提交且工作区无改动」才可信（`git log -1 --format=%ct -- <文件>`）。
  产物提交时间晚于报告文件提交时间 → 红（产物后置 = 未交付）。
  用 git 时间是因为它不在作者笔下：要伪造得改提交历史，成本高且在 review 里看得见。
- **如实记未核验（不判红）**：任一侧取不到可信的 git 提交时间（报告未提交 / 未跟踪 / 有未提交改动）
  时，本产物记为未核验，不参与先后比对，也不退回 mtime 或 `reportedAt`。
  输出会明说有多少个未核验，让「没核到」可见，而不是悄悄当成通过。
- **残留缺口（如实写）**：报告与产物在**同一个提交**里时，git 给不出先后；
  「先在会话里说已落地、半小时后补做并一起提交」这种情况，自动检查看不出，
  只能人工比对提交时间与会话时间。别把 R6 当成挡得住一切。
- **人工**：报告与产物跨提交时的先后（`git log` 逐条看）、同名产物被覆盖后
  报告引用的是哪一次。

### R7 没有产物就明说

- **必须写**：纯调研/口头结论可以没有产物，但块里必须写 `noArtifactsReason`，
  且正文不得出现"已落地/已通过/零差异"。有产物时不要写这个字段。
- **自动**：`artifacts` 为空时必须有非空 `noArtifactsReason`；非空时反之。
- **人工**：这个理由是否成立（比如"只是读代码"却报了像素结论）。

## 怎么查

- 自动：CI 前端 job 第 17 步 `npm run audit:reports`（已接入，PR 上真跑）；
  本地同命令可先跑。
- 人工：有没有落盘成 `docs/evidence/<slug>/README.md`（会话里的结论 lint 看不见）、
  R1 的"是不是这次产物"、R2 的"是不是这次运行"、R3 的分辨率与范围、
  R4 的语义归类、R5 的远端与 PR、R6 跨提交的先后与同提交内的"事后补做"、
  R7 的理由——逐条按上面标注核对。

## 自查清单（贴进报告前逐条打勾）

1. 每个产物有路径 + 字节数 + sha256，或写明为什么没有哈希。
2. 每条"通过"有命令名和退出码，正文有一行原始输出。
3. 每条"不变/零差异"有方法、阈值、分辨率、张数、范围。
4. 推断句标了 `[推断]` 并写了依据；实测句没有混进"应该"。
5. 提交/推送/PR 状态写全；被报告的工作与报告文件分开。
6. 报告文件提交时间晚于所有产物时间（`reportedAt` 只是辅助；报告未提交时退回人工核）。
7. 没有产物时写了 `noArtifactsReason`。
8. 报告已落盘成 `docs/evidence/<slug>/README.md`——只在会话里说过的，等于未受检。
