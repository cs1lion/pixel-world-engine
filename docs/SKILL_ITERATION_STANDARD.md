# Skill 自迭代改造规范（X3）

> 适用：改造 / 迭代本仓任一 skill 或工作流文档（`docs/agents/` 下的文件、`CLAUDE.md` 的 Agent skills 节、将来入仓的 skill 定义）。
> 用法：先按 §7 做四问诊断并报结果；再按 §2–§4 改造；交付前按 §6 五问作答，并按 §5 给每一项标验证边界。
> 与纪律文档的关系：本文是 [ENGINEERING_DISCIPLINE.md](file:///D:/project/pixel-world-engine/docs/ENGINEERING_DISCIPLINE.md#L377-L383) 中 **X3** 条款的展开文本。判据数值、闸门清单、阈值一律以纪律文档为准；本文只规定 skill 文档必须具备的结构、证据形态与汇报口径。
> 状态标签：沿用纪律文档开头的三态标签（`[已实现]` / `[人工步骤]` / `[尚未实现]`）。`[需人工]` 是**标注**不是第四态，二者并列写（见 §4.3）。
> 编号：本文节号稳定，只追加不改号；跨文档引用写「SKILL_ITERATION_STANDARD.md §N」（L3 / M3）。

## 1. 定位与适用范围

### 1.1 本文回答什么

把「依赖 AI 理解与执行的说明文档」改成「工作流程 + 工具可用 + 结果可验证 + 能持续反馈与改进」的工作系统，并给出四件事的可执行判据：**怎么算有、怎么算没有、证据落在哪、谁来判**。

### 1.2 适用对象

- 仓内 skill 定义与工作流文档：`docs/agents/` 三份、`CLAUDE.md` 的 Agent skills 节，以及后续任何入仓的 skill 文件。
- 任何一次对 skill 的改造、补写、重构、换代。
- 一次性的任务要求**不适用**本文；只有长期规则才进规范（见 §2.4 最后一行）。

### 1.3 不适用

- 不改既有 40 条纪律的判据与阈值。出现分歧按 §9.3、§9.4 处理。
- 仓外 skill（例如装在本机 skills 目录的规范文件）不入仓、不按本文验收；引用口径按 E5，只认已提交或可还原的材料。
- 不替代 V1–V5 的验证分层。本文只要求在 skill 文档里把验证**写成可执行的条目**（判据形态按 V2 / E1，本文不重述）。

### 1.4 判定权与优先级

1. 证据类条款优先：E1、E4、E6、W2。
2. 结构类其次：X1、X2。
3. 流程类（本文）再次。
4. 预算 / 性能（B 系列）与文档编号（L3、M3）按各自触发条件执行。
同一事实同时命中多条时按上面顺序执行，但**不按「更严」自动替用户选边**；冲突按 §9.3 的条件判定。

### 1.5 适用范围与排除

「适用」不看这份文件**像不像** skill 文档，看它**有没有被本仓改写过**。判定只用下面三步，每一步都能从 git 或文件内容机械复核。

**判定顺序**

1. **先找上游来源标记**：文内是否出现外部包名或安装命令（`mattpocock/skills`、`setup-matt-pocock-skills`、`backnotprop/pstack`）。没有 → 它本来就是本仓的文档，**在范围内**，判完。
2. **有上游标记 → 查三样本地改写证据，命中任一条即在范围内**：
   - a) `git log --follow --numstat -- <文件>` 里，除首次导入那次提交外，还有一次提交对该文件**增删行数都不为 0**（改写既有行，不是纯追加）；
   - b) 文件里有 `## 本仓库现状` 小节，或以「本地补充」开头的一段；
   - c) 文件里出现本仓身份串：`pixel-world-engine` 或 `cs1lion`。
3. **三条都不命中 → 判「借用且未改写」，排除**：不套用 X3，不要求三件套，不做 §7 诊断。

**为什么这类文件该排除**

- 它是外部约定的**投影**：词表、路径、开关换成本仓的，流程本身定义在上游。给它补三件套等于在本仓造第二份流程定义——上游一更新整段替换，第二份要么被冲掉，要么与上游分叉。两种结果都比「不套用」更差。
- 做 §7 诊断在这种文件上必然得出「缺三件套」，而这个结论在上游被改写前**不可能被消化**：补了会被覆盖，不补就一直红。一份永远红又修不掉的清单，最后没人会看。

**进入范围的开关：一次本地改写**

第 2 步任一条件一旦变真，文件**自动进入范围**，不需要人工复议，也不需要在本节登记。判据落在 git 与文件内容上，所以它可判定：下一次有人在这个文件里写下只对本仓成立的一句话，`git log --follow --numstat` 就会出现一次非零增删，或文件里出现本仓身份串。

## 2. 四块结构：判「有」的最低证据

四块是验收维度，不是章节标题。每块必须能被第三方按「证据落点」复核；给不出证据的，即使文书写得很长也算「没有」。

### 2.1 工作流程（Feature Map）

| 检查项 | 「有」的最低证据 | 「没有」的表现 |
| --- | --- | --- |
| 任务 / 步骤可点名 | 每个步骤有编号，写出输入、输出、执行条件 | 只有「先理解 → 再分析 → 然后实施」这类动词序列 |
| 依赖与分支可读 | 图上标出「若 A 则走 B」的条件与失败去向 | 只有一条直线；失败时写「再试一次」 |
| 入口唯一 | 每步指向任务清单的一条与脚本清单的一个入口，或一个 `[需人工]` | 同一动作在 README 与 agent 文件里各有一套说法 |
| 结束时有事可查 | 步骤结束时有产物或读数 | 步骤以「确认完成」结尾 |

证据落点：流程图在本文档内（§3.1）；任务与入口在 §3.2 / §3.3。

### 2.2 工具能力（CLI）

| 检查项 | 「有」的最低证据 | 「没有」的表现 |
| --- | --- | --- |
| 确定性步骤有入口 | 可复制的 `npm run <name>` 或 `node <path>`，当前树能跑 | 写「可以用某脚本」，仓里没有这个脚本 |
| 退出码可判 | 0 = 通过；非 0 = 失败，且失败原因可读 | 只打印日志、退出码恒 0 |
| 输入输出可固定 | 输入（文件 / 参数 / env）、输出（文件 / stdout）写清，可重复 | 依赖手输入、交互式提问、仓外服务且无替代 |
| 状态诚实 | 不存在的入口标 `[尚未实现]`；不能固化的标 `[需人工]` | 把「计划要写」写成「已有」（E6 违规） |

### 2.3 校验机制

| 检查项 | 「有」的最低证据 | 「没有」的表现 |
| --- | --- | --- |
| 完成判据可重跑 | 命令 + 期望读数 + 判绿口径三样齐全（V2 / E1） | 「检查一下是否正常」 |
| 判据与比较对象同源 | 写出 recorder / group / window / units 四项（C3） | 拿另一棵树、另一记录器的读数当基线 |
| 有反向用例 | 至少一个已知应失败的样本，跑起来必须红 | 只有正例；红了也没人知道 |
| 人工项有核验对象 | 写清看哪张图、哪个文件、哪条读数 | 「人工确认」四个字单独成立 |

判据形态按 V2 / E1 执行，本文不重写命令与阈值。

### 2.4 反馈闭环

| 检查项 | 「有」的最低证据 | 「没有」的表现 |
| --- | --- | --- |
| 反馈有登记处 | issue 编号、台账文件或优化日志；字段：问题、来源、日期 | 反馈只留在对话里 |
| 同类问题有吸收点 | 上一次反馈被哪条条款或脚本吸收，能指到编号 | 同一问题第三次出现仍靠提醒 |
| 闭环有证据 | 「问题 → 条款 / 脚本 → 验证命令与结果」三段齐全 | 写「已修复」但无复跑记录 |
| 单次需求与长期规则分开 | 一次性要求留在任务清单；长期规则才进规范 | 把一次的要求写成永久禁令，规则无限膨胀 |

### 2.5 总体通过条件

- 四块都有最低证据 → 只能称「已改造」。
- 缺任意一块 → 只能称「部分改造」，并逐块列出缺口。
- 不得用「整体感觉清晰了」替代逐块判定（C1：全称结论要附枚举）。

## 3. 三件套的最小要求

三件套缺任何一件时，§2 对应维度直接判「没有」。

### 3.1 工作流程图

- **形式**：mermaid 或 ASCII 均可，必须能纯文本读。
- **必含**：触发条件、步骤编号、每步输入 / 输出、分支条件、失败去向、回退点。
- **颗粒度下限**：一个节点 = 一次会话内能完成 + 能独立验收；一句话里超过三个动词短语就拆。
- **对应关系**：每个节点必须能被 §3.2 的任务 ID 指到。只有图、没有任务编号，算没画。

### 3.2 任务清单

列必须齐全，缺列算没有：

| ID | 任务 | 输入 | 输出 | 入口 | 判据 | 状态 | owner |
| --- | --- | --- | --- | --- | --- | --- | --- |

- **ID**：稳定，只追加不复用（L3）。
- **输出**：必须是具体产物——文件、读数、提交、issue、截图；「完成」不是产物。
- **入口**：指向 §3.3 的一行，或 `[需人工]`。
- **判据**：按 §2.3 的三段写；允许引用已有条款编号，不重抄命令。
- **状态**：三态标签 + `[需人工]` 并列。
- **owner**：agent / 人 / 待认领；不得留空（L1）。
- **颗粒度下限**：一条任务 = 一次可检查的产出。「完善」「优化」「梳理」「看看」不能单独构成任务名。

### 3.3 脚本清单

列必须齐全：

| 脚本 | 入口命令 | 输入 | 输出 | 退出码含义 | 在 CI | 状态 |
| --- | --- | --- | --- | --- | --- | --- |

- 每行的入口命令必须可直接复制执行。
- 「在 CI」列必须与 `.github/workflows/ci.yml` 的实物一致（E6）；不存在就写「否」并标 `[尚未实现]`。
- 仓外脚本或尚未存在的脚本：写清缺什么、谁补、补完接哪条闸。
- **只读脚本与判红脚本分列**。只输出读数、退出码恒 0 的，不得放在「判红」一栏（C4 的 `check-glow-contrast` 教训）。

### 3.4 互指约束

1. §3.2 每条的「入口」必须落在 §3.3 的一行或 `[需人工]`。
2. §3.1 每个节点必须在 §3.2 出现，且至少一条任务以它的产物为输入。
3. 不许有孤儿条目：脚本清单里没有任何任务引用的脚本，要么补任务，要么删掉。

## 4. 工具化与 `[需人工]` 标注

### 4.1 值得固化的判据

四条同时满足才固化：

1. 同输入同输出（确定性）。
2. 预计会被重复执行 ≥ 2 次。
3. 判据能写成退出码。
4. 不需要语义、事实或审美判断。

固化后必须给统一入口：优先 `npm run <name>`，其次 `node <path>`；只把命令写进 README 不算工具化。已有 `scripts/` 下脚本的步骤，不许改标成人工。

### 4.2 必须标 `[需人工]` 的情形

出现任一条就必须标：

1. 需要外部证据，而仓里没有采集手段。
2. 判据是语义、事实或审美，机器分不了。
3. 依赖仓外资源（浏览器、人眼、第三方服务、未入库材料）。
4. 动作会改别人的树或需要授权（push、merge、删 worktree、改 `main`）。

### 4.3 标注格式与判绿口径

```text
[需人工] 谁跑：<角色 或 待认领>；判绿口径：<可观察结果>；未覆盖：<本次不验证的部分>
```

- **谁来跑**：必须落到具体角色（`cs1lion` / 某条线 / 待认领）。「有人看一下」不算。
- **怎么判绿**：必须可观察——截图、读数、文件 sha、issue 关闭、签字记录。不能是「看起来对」。
- **判绿之后**：在任务清单把状态从 `[需人工]` 改为 `[人工步骤]`，并附证据位置；没有证据的一律按 §5.4 处理。

### 4.4 禁止事项

- 把已有脚本的步骤标成 `[需人工]`，用人工标签绕过工具化。
- 用「AI 评估通过」代替人工确认（§5.2 不得升级为 5.3）。
- 标了 `[需人工]` 却不写谁跑、怎么判绿、未覆盖什么。

## 5. 四类验证边界（不得混用）

### 5.1 自动验证通过

- **定义**：命令退出 0，读数可复算，命令可重跑。
- **证据**：命令原文 + exit code + 本次读数（E1）。
- **限制**：只证明「命令通过」，不证明「命令测的是意图」（C3 / C4）。

### 5.2 AI 评估通过

- **定义**：模型对内容做语义判断，给出理由与所依据的条款编号。
- **证据**：被评对象 + 判据条目 + 理由。不可复算。
- **汇报用语**：只能写「AI 评估通过（依据见 …）」，不得计入自动验证数。

### 5.3 人工确认通过

- **定义**：人执行确认，并留下可复核痕迹。
- **证据**：确认人 + 时间 + 确认对象（文件 sha / 截图 / 行号 / issue 回复）。
- **汇报用语**：「已人工确认（对象：…，确认人：…，时间：…）」。

### 5.4 人工确认但未被验证

- **定义**：人做了动作但没有可复核证据，或只有口头「看过了」。
- **汇报用语**：只能写「人工确认，未验证」。保留 E4 的 `[推断]` 直到补证据。
- **禁止**：升级为 5.3；写成「已验证」。

### 5.5 为什么不得混用

1. **证据强度不同**：5.1 / 5.3 可被第三方复核，5.2 / 5.4 不能。
2. **混用等于把「我看过」写成「机器验过」**，这正是 E1 / E4 禁止的「宣称验证通过」。
3. **每类都有盲区**：5.1 不测意图，5.2 不可复算，5.3 / 5.4 依赖人。混称会掩盖盲区。
4. **返工动作不同**：5.1 红改实现；5.2 不过改判据或补证据；5.3 不过改交付；5.4 先补留痕。

### 5.6 与「有证据，不宣称验证通过」对齐

- 任何「通过」只能来自 5.1 或 5.3。
- 没有证据的只能写 5.2 / 5.4，或按 E4 标 `[推断]`。
- 交付里出现「已验证」而找不到证据 = E1 违规；出现「CI 会跑」而 `ci.yml` 里没有 = E6 违规。

## 7. 诊断模板（可复制）

### 7.1 第一步：四问诊断

```text
skill：<路径 或 名称>
1. 工作图：任务步骤 / 输入输出 / 依赖 / 分支 → 结论：<能继续 | 阻塞点>
   证据：<文件 + 小节名>
2. 工具能力：已有入口 / 可靠且确定性的步骤 / 缺口 → 结论
   证据：<文件 + 小节名>
3. 校验机制：现在怎么判完成 / 能否复跑 / 是否只靠文字 → 结论
   证据：<文件 + 小节名>
4. 反馈闭环：反馈登记在哪 / 上次反馈被什么吸收 → 结论
   证据：<issue 或台账位置>
诊断结论：<能继续 | 阻塞点 1..n>
最小下一步：<一条，不做大范围重构>
```

诊断先于改造；诊断输出就是这张表，不许换字段重写。

### 7.2 第二步：与用户确认验收标准

依次问（能从上一步证据回答的不要问）：

1. 好结果是什么样的？
2. 哪些要求必须满足，哪些只是偏好？
3. 最不能接受什么问题？
4. 过去哪些事反复出现？
5. 哪些环节必须人工确认？
6. 哪些环节可以由 Agent 自动执行？

规则：
- 先审已有材料，只问**缺失或矛盾**的项；最多 3 个问题。
- 每个问题必须写「为什么仓内材料回答不了」。
- 不让用户重述已有信息；不把已写明的条款再问一遍。

### 7.3 三件套检查清单

```text
[ ] 工作流程图：节点含输入 / 输出 / 条件 / 失败去向；每节点可指到任务 ID
[ ] 任务清单：ID / 任务 / 输入 / 输出 / 入口 / 判据 / 状态 / owner 八列齐全
[ ] 脚本清单：入口可复制执行；退出码含义明确；CI 与 ci.yml 一致
[ ] 互指：任务→脚本（或 [需人工]）；节点→任务；无孤儿条目
[ ] 验证边界：每个交付项标 5.1 / 5.2 / 5.3 / 5.4 之一
```

### 7.4 诊断阶段的硬约束

- 先诊断、不动手；验收标准未确认前不做大范围重构。
- 结论必须能指到文件与小节；「文档比较乱 / 不够清晰」不是结论，要指到缺哪块判据（C1）。
- 不做「为了重构而重构」：已有有效设计原样保留，只补缺的那块。
- 诊断结果先报给用户一次，再进入改造。

### 9.3 冲突项与适用条件

**冲突 A（硬冲突）：本文「不要立即大范围重构」↔ X1「先改环境，让错不可能发生」**

两者不互相取消，按条件分工：

- **X1 适用**：①已经发生一次可命名、可复现的错误；②修复能落成测试 / lint / CI / 结构闸；③改动 ≤ 1 个模块，且不改既有判据数值。
- **本文「先诊断」适用**：①首次接手一个 skill；②验收标准尚未与用户确认；③结构修复会动 ≥ 2 个模块，或改判据 / 阈值 / 合同。
- **中间情形**：先落「一条最小结构闸 + 诊断报告」，再请用户确认是否扩围。
- **禁止**：把「先诊断」当成不出手的理由；把「X1」当成先改后问的许可。
- **留痕**：走 X1 的，交付里写「本可避免的错误是什么 / 环境为什么允许它发生」；走本文的，诊断报告里写「阻塞点 + 最小下一步」。

**冲突 B（措辞冲突）：人工核验 ↔ E4**

- 原指南允许「语义、事实等主观判断保留人工核验」；E4 要求「不得把 `[推断]` 留在交付文档里当事实」。
- 落成：人工核验只在**有留痕**时算 §5.3 通过；无留痕一律 §5.4，并保留 `[推断]` 直到补证据。
- 反例：只写「人工确认通过」而不给对象 → 按 §5.4 处理，并按 E1 视为违规。
